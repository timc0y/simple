## Proposed implementation

Rename the database field through the existing migration mechanism, while keeping the old public API name as a compatibility alias for 90 days.

1. Add a migration that renames `old_field` to `new_field` in place. Preserve nullability, defaults, indexes, constraints, and existing values.

2. Make the service’s internal model and persistence layer use only `new_field`.

3. At the API boundary:
   - Accept both `oldField` and `newField`.
   - Prefer `newField` when both are supplied.
   - Reject conflicting values rather than choosing silently.
   - Return `newField` for new clients.
   - Continue returning `oldField` for clients that use the old representation, or provide an explicit version/content-negotiation rule if the API already has one.

4. Mark `oldField` deprecated and document its removal date. Instrument requests using it so removal is based on observed traffic.

5. Verify the migration before and after deployment:
   - Every pre-migration value is present under `new_field`.
   - Reads and writes through both API representations produce the same stored value.
   - Conflicting input is rejected.
   - Rollback restores service behavior without losing customer data.
   - Both old and new clients pass contract tests.

6. After 90 days, when old-client traffic is zero, remove the old API alias, deprecation handling, telemetry, and any compatibility tests. Remove the old database name only if the migration did not already rename it in place.

The database migration owns persisted state; the API boundary owns compatibility. Do not add permanent dual writes or a second schema unless the actual migration mechanism cannot safely rename the field.
