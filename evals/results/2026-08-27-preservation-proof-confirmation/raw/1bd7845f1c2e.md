Implement the rename as one bounded compatibility change:

1. Add a migration using the existing schema mechanism to rename the persisted field. Preserve all values and make the migration reversible.
2. Change the domain model and internal code to use the new field name.
3. Add one API adapter that maps the deprecated public field to the new representation on input and output. Keep the new representation canonical; do not maintain separate stored fields or dual writes.
4. During the 90-day deprecation period:
   - accept both old and new request fields;
   - return the representation appropriate to the existing API version or negotiation mechanism;
   - define deterministic behavior if both fields are supplied, preferably rejecting conflicting values.
5. Add deprecation messaging and documentation for the old field.
6. Verify migrated records, reads and writes through both API representations, rollback behavior, and removal criteria.

After 90 days, remove the old API mapping only when old-client traffic is zero or the compatibility owner explicitly approves an extension. The persisted old name can then remain absent; only the new field is authoritative.
