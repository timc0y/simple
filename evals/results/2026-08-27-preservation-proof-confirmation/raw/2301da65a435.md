Ship the direct one-shot CLI. The daemon adds substantial operational and code complexity without evidence that residency solves the measured problem.

Establish:

- Cold-start timing split into process startup, module loading, command setup, and the remote operation.
- Import-graph evidence showing the path from the common module through the generator to the compiler.
- That the generated JSON can be consumed directly with identical contents, validation, and command results.
- Before-and-after cold-command latency across representative commands, including repeated runs.
- That service installation, recovery, and daemon behavior provide no required user capability today.

Test first by removing the generator from the runtime import path. Reference the generated JSON directly, or put only its path in a lightweight module if the command requires a filesystem path. Preserve the existing command surface and safety checks, then compare latency and behavior independently through the CLI.

If this restores the lost startup time and the tests pass, remove the daemon’s HTTP server, service installation, second composition root, duplicate route table, lazy loader, parity tests, and status/recovery commands. Remove the generator or compiler only from the runtime dependency path; retain them if the build still needs them.

A resident process becomes justified only when a measured requirement needs live continuity across commands—such as state or a session that cannot be represented as durable data—and the resulting benefit is worth the added installation, recovery, ownership, and failure burden.
