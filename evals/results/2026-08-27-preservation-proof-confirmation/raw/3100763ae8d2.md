Ship the existing one-shot CLI. The evidence supports a startup/import regression, not a need for a resident service.

### Evidence to establish

- Profile cold-start latency and import time before and after the dependency change.
- Trace whether the generator and compiler are loaded only to obtain the path constant.
- Confirm the generated JSON is an existing source of truth and can be consumed directly.
- Run the existing command, grammar, safety, result, and durable-record tests.
- Repeat the benchmark across cold processes; do not infer a bundling benefit without measuring it.

### Smallest change to test first

Remove the generator import from the common module. Use the existing generated JSON or a local path constant directly, depending on which is the actual owned artifact. Do not add bundling yet.

If cold latency improves while command behavior remains unchanged, the direct CLI has addressed the demonstrated problem.

### Remove if successful

After checking for other consumers, remove the daemon prototype and its supporting surface:

- HTTP server and service installation
- second composition root
- duplicate route table
- lazy route loader
- parity tests
- service status and recovery commands

Keep the ordinary CLI path and the durable completed task records.

### When residency becomes justified

Reconsider a resident process only when a measured requirement needs continuity across commands—such as live session state or a reusable connection—and that requirement cannot be represented as durable data or met through the one-shot path. A 180 ms startup cost alone is insufficient justification, especially after the import chain is corrected.
