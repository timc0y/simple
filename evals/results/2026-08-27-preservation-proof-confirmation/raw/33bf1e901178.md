## Ship

Keep the one-shot CLI. Do not ship the daemon or bundling yet.

The measured problem is process startup, and the repository shows no requirement for cross-command continuity. A resident daemon would add a second runtime path and operational surface without addressing an identified capability need.

## Evidence to establish

- Measure cold CLI latency before and after the import change, separating startup, imports, and the remote operation.
- Confirm the common module needs only the generated JSON path, not generator behavior.
- Verify the generated JSON is present, valid, and readable after the process exits.
- Run existing command behavior and safety checks against the direct CLI.
- Confirm no external consumer depends on the daemon or its unpublished architecture.

## Smallest change to test

Move the path constant to the existing lightweight owner, or define it directly where it is consumed. Remove the runtime import of the generator so the compiler is not imported transitively.

Then compare cold latency and command results. Do not bundle until profiling shows bundling is the remaining cost.

## Remove if it succeeds

Delete the unneeded daemon machinery:

- HTTP server and service installation
- second composition root
- duplicate route table
- lazy route loader
- parity tests for the duplicate path
- service status and recovery commands

The direct CLI remains the sole command path, and completed task records remain durable.

## When residency becomes justified

Reconsider a resident process only when measurements show a required capability depends on continuity across commands—such as retained in-memory state, streaming, watches, or an unavoidable warm connection—and that capability cannot be represented as durable data or supplied through the ordinary CLI path.
