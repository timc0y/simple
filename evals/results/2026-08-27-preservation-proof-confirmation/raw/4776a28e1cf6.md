Implement the rename as a bounded compatibility migration.

### Outcome

The new persisted field and API field become canonical. Existing clients and retained records continue working for the promised 90-day deprecation period.

### Implementation

1. Add the new database field with the existing type and constraints.
2. Backfill it from the old field and verify every retained record.
3. Update the model to read the new field and write both fields temporarily.
4. Update the API boundary to:
   - accept both old and new request names;
   - reject requests that provide conflicting values;
   - return the new name as canonical;
   - retain the old response name during the deprecation period, using the existing API versioning mechanism if clients cannot tolerate an additional field.
5. Measure old-field API usage. After 90 days, when it reaches zero:
   - stop accepting and emitting the old API name;
   - stop writing the old database field;
   - remove the old field in a later migration.

Do not silently overwrite conflicting old and new values. Preserve the old database field until rollback and migration verification are complete.

Verify:

- old and new clients can read and write the value;
- old and new API representations map to the same stored value;
- all existing records survived the backfill;
- failed migrations and application rollback remain recoverable;
- old-client traffic is zero before removing compatibility.
