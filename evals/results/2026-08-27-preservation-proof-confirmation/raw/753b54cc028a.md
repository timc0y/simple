Implement the rename as a bounded compatibility migration:

1. Add the new persisted field using the existing migration mechanism. Backfill it from the old field, preserving values, nullability, defaults, indexes, and constraints. Keep a backup and a reversible migration path.

2. Make the new field canonical in the service. The public API layer should translate between the old and new names; storage details must not leak into clients.

3. During the 90-day deprecation period:

   - Accept both API names.
   - If both are supplied with different values, reject the request.
   - Write only the canonical new value.
   - Return the representation required by the existing API version or negotiation mechanism, so old and new clients continue to work.
   - Record usage of the old representation.

4. Verify the migration independently:

   - Compare old and new stored values and record counts.
   - Test old and new clients.
   - Test conflicting input and null/default cases.
   - Exercise rollback and recovery from backup.
   - Confirm the old-name usage metric is reliable.

5. After 90 days, remove the old API adapter and deprecation documentation only when old-client traffic is zero. Then remove the old persisted field through a separately verified migration.

Do not maintain two independent sources of truth or create a permanent API version. The new persisted field owns the data; the old name exists only as a temporary boundary adapter.
