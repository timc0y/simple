Ship the one-shot CLI and remove the daemon prototype. The evidence points to startup/import overhead, not a capability requiring process continuity.

### Evidence to establish

- Measure cold-start latency before and after the change, separately from remote-operation time.
- Profile module loading to confirm the path is:

  `common module → generator → compiler`

- Verify the command reads only the generated JSON artifact.
- Check whether the generator or compiler has other real consumers.
- Confirm command results, validation, safety checks, and durable task records remain unchanged.

### Smallest change to test first

Change the common module to reference or load the generated JSON directly. Keep the generator in the build or generation path if it is still needed, but keep it out of the command’s runtime dependency graph.

Measure repeated cold invocations and run the existing command-behaviour tests. Do not bundle yet; test the narrower, observed cause first.

### What can be removed if it succeeds

If the direct artifact change removes the regression, remove the machinery added only to compensate for startup time:

- HTTP daemon and service installation
- second composition root
- duplicate route table
- daemon parity tests
- service status and recovery commands
- lazy route loader
- runtime generator and compiler dependencies, if no other consumer needs them

Before deletion, check exports, scripts, dynamic loading, generated-code workflows, and operational references.

### When residency becomes justified

Add a resident process only when a measured requirement needs continuity across commands—such as live session state, a persistent connection, or a warm cache—and that state cannot be represented safely as durable data.

That requirement should have a quantified benefit that remains after import and startup costs are addressed. Until then, the ordinary one-process command path is the sufficient owner.
