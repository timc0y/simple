Ship the one-shot CLI. Do not ship the resident daemon.

The repository facts support this boundary: one local operator runs commands, each command performs one short remote operation, completed task records are durable, and no current capability requires continuity between commands. The regression is startup/import time, not remote execution.

Establish these facts first:

- Measure cold-start latency separately from command execution and remote-operation latency.
- Trace the import graph and quantify the generator and compiler load.
- Confirm that the common module only needs the generated JSON/path value.
- Verify that the generated artifact is current and has a clear generation step.
- Compare CLI behaviour, safety checks, results, and durable records before and after the change.

Test the smallest change first: make the common module consume the generated JSON or path directly, removing the runtime import of the generator and compiler. Measure that change before considering bundling.

If it succeeds, remove the daemon prototype and its displaced machinery:

- HTTP server and service installation
- second composition root and duplicate route table
- lazy route loader
- parity tests for the two paths
- service status and recovery commands
- daemon-specific documentation, configuration, and dependencies

Preserve the command grammar, results, safety checks, and readable completed records. Prove those through the public CLI, independently of the removed implementation.

A resident process becomes justified only when measured requirements show that commands must share live state across invocations—such as a session, watch, connection, or cache—and that this continuity cannot be represented as durable data. The requirement must also show a material benefit after the import fix, with explicit ownership, failure, recovery, and lifecycle behaviour.
