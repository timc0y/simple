Implement the rename as a bounded compatibility migration.

### Design

- Make `new_field` the canonical persisted field.
- Use the existing schema migration mechanism to rename or backfill `old_field` into `new_field`.
- Keep a single API-boundary adapter for the 90-day deprecation period:
  - New clients send and receive `new_field`.
  - Old clients continue sending and receiving `old_field`.
  - Both forms map to the same canonical `new_field`; do not maintain two sources of truth.
- Use the repository’s existing client/version or content-negotiation signal to select the API representation. If no such signal exists, that is the remaining design blocker.

### Implementation order

1. Add boundary translation and validation for both representations.
2. Add the reversible schema migration, with backup and verification.
3. Deploy compatibility handling before migrating stored records.
4. Migrate retained customer data to `new_field`.
5. Verify reads, writes, old-client responses, new-client responses, and rollback.
6. Measure old-field traffic during the 90-day window.
7. After the promise expires and old-client traffic reaches zero, remove the adapter and old API representation.

### Proof and safety

Verify that:

- Every existing record has the new persisted field with unchanged meaning.
- Old and new API clients observe equivalent values.
- Writes through either representation update the same stored value.
- Migration rollback restores service and data.
- No old-client traffic remains before deleting compatibility code.

This preserves customer data and the published contract while making the new field the sole source of truth.
