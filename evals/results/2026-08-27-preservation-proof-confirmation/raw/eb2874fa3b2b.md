Implement the rename as one canonical internal model with a bounded compatibility adapter at the API boundary.

### Outcome

After the 90-day deprecation period:

- The persisted field has the new name.
- The public API uses the new representation.
- Customer values remain unchanged.
- Old clients continue working during the transition.
- The old field and compatibility code can be removed when old-client traffic reaches zero.

### Implementation

1. Inventory every database, query, serializer, validator, job, and API client reference to the old name.

2. Use the existing migration mechanism for the persisted rename.

   - If schema and application deployment are atomic, use a reversible column rename and update all consumers together.
   - If old and new application versions may overlap, use expand-and-contract: add the new field, backfill it, read the new field with a temporary fallback, write both fields, then remove the old field after verification.

3. Make the service’s internal model use only the new name.

4. Add one API-boundary adapter for the 90-day period:

   - Accept the old and new request fields.
   - If both are supplied with different values, reject the request.
   - Emit the representation selected by the existing API version or capability mechanism.
   - If no such mechanism exists, establish one before implementation; returning both fields may break clients that reject unknown properties.

5. Record usage of the old representation. Keep the adapter, documentation, and telemetry removal condition explicit: the 90-day promise has ended and old-client traffic is zero.

### Proof

Verify independently that:

- Migration preserves every stored value, including nulls and defaults.
- New API requests and responses use the new representation.
- Old clients continue to work during the deprecation period.
- Conflicting old/new inputs are rejected safely.
- Rollback restores the prior schema and API behaviour.
- No references to the old persisted field remain before its removal.

The exact field names, API versioning mechanism, and deployment overlap policy are not present in the repository context, so those determine which migration branch is safe.
