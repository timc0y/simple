# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days. Old and new clients must both work during that transition.
- No facts are known about operators, scale, failure consequences, security, or other users or consumers.

## Preserve

- Retained customer records.
- The 90-day old-field API promise and support for both old and new clients.
- `CustomerSerializer`'s deprecation alias: it accepts either field name, rejects conflicting values, and emits both names from one internal value during the bounded transition.

## Current boundary

- The service supports both customer field names during the 90-day transition. No other compatibility, operational, scale, failure, or security boundary is known.

## Ordinary paths

- `CustomerSerializer` owns customer request parsing and response serialization.
- Use the existing migration runner for schema changes.
- Use `CustomerSerializer`'s existing deprecation-alias facility for the field-name transition.

## Proof

- Verify stored data, both API representations, rollback, and eventual removal of old-name handling.

## Reconsider when

- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.
- Reconsider the profile when facts about other users, operators, scale, failure consequences, security, or compatibility commitments are established.
