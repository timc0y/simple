# Simple

## Reality

- Stage and users: Production service with published API clients.
- Operators: Unknown.
- External consumers: Published API clients depend on the API.
- Public contracts: The old customer field name remains promised for 90 days. Old and new clients must both work during that period.
- Persistent production data: Retained customer records must survive schema changes.
- Compatibility commitments: `CustomerSerializer` must accept either field name, reject conflicting values, and emit both names from one internal value during the bounded transition.
- Scale and failure consequences: Unknown.

## Preserve

- Published client compatibility during the 90-day transition.
- Retained customer records.
- One internal customer value represented by both field names.
- Rollback and removal verification.

## Current boundary

- Customer request parsing and response serialization belong to `CustomerSerializer`.
- Schema changes belong to the existing migration runner.
- The service supports old and new customer field names only for the bounded transition.

## Ordinary paths

- Use `CustomerSerializer` for request parsing and response serialization.
- Use the existing migration runner for schema changes.
- Use its deprecation-alias facility for the field-name transition.

## Proof

- Verify stored customer data.
- Verify both API representations.
- Verify rollback.
- After 90 days and zero old-field traffic, remove old-name handling and verify removal.

## Reconsider when

- Reconsider the compatibility path after 90 days and zero old-field traffic.
- Reconsider other design assumptions when facts about operators, scale, failure consequences, security, or additional compatibility obligations become known.
