# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days. Old and new clients must both work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retained customer records and the 90-day API promise for the old customer field name.
- The transition must reject conflicting old and new field values.

## Current boundary

- The production service supports retained customer records and its published API clients. During the bounded field-name transition, it supports both API representations.

## Ordinary paths

- Use the existing migration runner for schema changes.
- `CustomerSerializer` owns request parsing and response serialization. Its deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value during the transition.

## Proof

- Verify stored data, both API representations, rollback, and removal of old-name handling.

## Reconsider when

- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.
