# Simple

## Reality

- Stage and users: This is a production service used by published API clients.
- Operators: No operator, release, or support facts are known.
- External consumers: Published API clients depend on its API.
- Public contracts: The old customer field name is promised for 90 days, and old and new clients must both work during that transition.
- Persistent production data: Retained customer records must survive changes.
- Compatibility commitments: The old customer field name remains supported for 90 days.
- Scale and failure consequences: No scale or failure-consequence facts are known.

## Preserve

- Retained customer records.
- The 90-day API promise.
- Support for both old and new clients during the transition.
- `CustomerSerializer`'s deprecation-alias behavior: it accepts either field name, rejects conflicting values, and emits both names from one internal value.
- The existing migration runner and verification coverage.

## Current boundary

- `CustomerSerializer` owns customer request parsing and response serialization.
- The existing deprecation-alias facility supports the bounded old/new field-name transition.
- Schema changes use the existing migration runner.

## Ordinary paths

- Use `CustomerSerializer` for request parsing and response serialization.
- Use its existing deprecation-alias facility for the field-name transition.
- Use the existing migration runner for schema changes.
- Verify stored data, both API representations, rollback, and removal through the existing verification coverage.

## Proof

- Verify retained customer records.
- Verify API requests and responses using both field names.
- Verify rollback.
- Verify removal after 90 days and zero traffic using the old field name.

## Reconsider when

- Remove old-name handling only after the 90-day promise has expired and old-field traffic is zero.
- Reconsider other design assumptions if new user, operator, scale, failure, security, or compatibility facts become known.
