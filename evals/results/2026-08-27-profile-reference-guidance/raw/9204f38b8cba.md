# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days. Old and new clients must both work during that transition.
- No users, operators, scale, failure, security, or compatibility facts beyond these are established.

## Preserve

- Customer records must survive schema changes.
- During the 90-day transition, accept either customer field name, reject conflicting values, and serialize both names from one internal value.
- Remove old-name handling only after 90 days and zero old-field traffic.

## Current boundary

- The service supports its published API clients and retained customer records. The stated API promise and production records establish this boundary.

## Ordinary paths

- Use the existing migration runner for schema changes.
- `CustomerSerializer` owns request parsing and response serialization. Use its deprecation-alias facility for the bounded field-name transition.

## Proof

- Verify stored data, both API representations, rollback, and removal of old-name handling.

## Reconsider when

- Reconsider the transition only when the 90 days have elapsed and old-field traffic is zero; then remove old-name handling.
- Establish additional facts before making decisions about users, operations, scale, failures, security, or compatibility beyond the stated API promise.
