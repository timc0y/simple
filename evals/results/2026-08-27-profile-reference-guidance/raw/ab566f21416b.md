# Simple

## Reality

- Stage and users: This is a production service with retained customer records.
- External consumers: Published API clients depend on the service. Both old and new clients must work during the field-name transition.
- Public contracts: The API promises the old customer field name for 90 days.
- Persistent production data: Retained customer records must survive the change.
- Compatibility commitments: The old customer field name remains supported for 90 days while the new name is introduced.
- Operators, scale, failure, and security: No facts are known beyond the existing migration runner and the required verification coverage.

## Preserve

- Retained customer records.
- The API contract for both old and new clients during the 90-day transition.
- Conflict rejection when both field names are supplied with different values.

## Current boundary

- `CustomerSerializer` owns customer request parsing and response serialization.
- Its deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value during a bounded transition.

## Ordinary paths

- Use `CustomerSerializer` and its existing deprecation-alias facility for the API representation transition.
- Use the existing migration runner for schema changes.

## Proof

- Verify stored customer data, both API representations, rollback, and removal.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.

## Reconsider when

- Reconsider removal only when the 90-day promise has ended and telemetry shows zero traffic for the old field name.
- No other reconsideration conditions are known.
