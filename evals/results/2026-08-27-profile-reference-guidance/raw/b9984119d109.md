# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days.
- Both old and new API clients must work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retained customer records.
- The 90-day old-field API promise and support for both client representations during it.
- Conflicting old and new field values must be rejected.

## Current boundary

- The service supports a bounded customer-field rename transition: one internal value is represented by both field names for published clients.

## Ordinary paths

- Use the existing migration runner for schema changes.
- `CustomerSerializer` owns request parsing and response serialization.
- Use its deprecation-alias facility to accept either field name, reject conflicting values, and emit both names from one internal value during the transition.

## Proof

- Verify stored data, both API representations, rollback, and old-name removal.

## Reconsider when

- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.
