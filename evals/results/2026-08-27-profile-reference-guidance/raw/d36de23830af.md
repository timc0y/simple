# Simple

## Reality

- This is a production service with published API clients.
- Customer records are retained production data.
- The API promises the old customer field name for 90 days.
- Old and new API clients must both work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retain customer records.
- Preserve the old customer field name for the promised 90-day period and support both old and new clients during that period.

## Current boundary

- The service supports published API clients and retained customer records. The API transition supports both customer field names through `CustomerSerializer`, which owns request parsing and response serialization.

## Ordinary paths

- Use the existing migration runner for schema changes.
- Use `CustomerSerializer` for customer request parsing and response serialization.
- Its deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value during the bounded transition.

## Proof

- Verify stored customer data, both API representations, rollback, and removal.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.

## Reconsider when

- Reconsider the transition design if the 90-day promise or zero-traffic removal condition changes, or if verification does not cover stored data, both API representations, rollback, and removal.
