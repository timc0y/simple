# Simple

## Reality

- Stage and users: This is a production service used by published API clients.
- Operators: No operator, release, or support facts are known.
- External consumers: Published API clients depend on its API.
- Public contracts: The old customer field name is promised for 90 days. Old and new clients must both work during that transition.
- Persistent production data: The service retains customer records.
- Compatibility commitments: The old field name must remain accepted and represented alongside the new name for the bounded 90-day transition.
- Scale and failure consequences: No scale or failure-consequence facts are known.

## Preserve

- Retained customer records.
- The published API contract for both old and new clients during the 90-day promise.
- The single internal customer value represented by either field name.

## Current boundary

- `CustomerSerializer` owns customer request parsing and response serialization.
- Its deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value during a bounded transition.
- Schema changes use the existing migration runner.

## Ordinary paths

- Use `CustomerSerializer` for request parsing and response serialization, including the existing deprecation-alias facility for the field transition.
- Use the existing migration runner for schema changes.

## Proof

- Verify stored customer data, both API representations, rollback, and removal.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.

## Reconsider when

- After 90 days and zero old-field traffic, remove the old-name handling and verify removal.
- Reconsider other design assumptions when facts about users, operators, scale, failure consequences, or compatibility become known.
