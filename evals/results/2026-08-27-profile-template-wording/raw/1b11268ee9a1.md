# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retained customer records.
- The old customer field name for the 90-day transition.
- Both old and new API clients must work during the transition.

## Current boundary

- `CustomerSerializer` owns request parsing and response serialization.
- Its deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value during a bounded transition.
- No other boundary facts are known.

## Ordinary paths

- Use the existing migration runner for schema changes.
- Use `CustomerSerializer`'s existing deprecation-alias facility for the field-name transition.

## Proof

- Verify stored data, both API representations, rollback, and removal.

## Reconsider when

- Remove old-name handling only after 90 days and zero old-field traffic.
