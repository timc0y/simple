# Simple

## Reality

- Stage and users: This is a production service with published API clients and retained customer records.
- Operators: No operator, release, or support facts are known.
- External consumers: Published API clients depend on the service API.
- Public contracts: The API promises the old customer field name for 90 days.
- Persistent production data: Retained customer records must survive changes.
- Compatibility commitments: Old and new clients must both work during the transition. Old-name handling may be removed only after 90 days and zero old-field traffic.
- Scale and failure consequences: No scale or failure facts are known.

## Preserve

- Retained customer records, both old and new API representations during the transition, rollback, and the existing migration runner.

## Current boundary

- `CustomerSerializer` owns request parsing and response serialization. Its deprecation-alias facility accepts either customer field name, rejects conflicting values, and emits both names from one internal value during a bounded transition.

## Ordinary paths

- Use `CustomerSerializer` for the field-name transition and the existing migration runner for schema changes.

## Proof

- Verify stored data, both API representations, rollback, and removal. Removal is valid only after 90 days and zero old-field traffic.

## Reconsider when

- Reconsider the design if the 90-day promise, the zero-traffic removal condition, the retained-record requirement, the serializer ownership, or the migration-runner workflow changes.
