# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days.
- Old and new clients must both work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Customer records must remain intact through schema changes and rollback.
- During the 90-day transition, either customer field name is accepted, conflicting values are rejected, and both names are emitted from one internal value.

## Current boundary

- The service supports both published customer-field representations during the promised 90-day transition.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.

## Ordinary paths

- Use the existing migration runner for schema changes.
- `CustomerSerializer` owns customer request parsing and response serialization.
- Use `CustomerSerializer`'s existing deprecation-alias facility for the bounded field-name transition.

## Proof

- Verify stored customer data, both API representations, rollback, and removal.

## Reconsider when

- New facts establish additional users, operators, contracts, or requirements beyond the known 90-day transition.
