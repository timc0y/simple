# Simple

## Reality

- Stage and users: This is a production service with published API clients.
- Operators: No operator facts are known.
- External consumers: Published API clients consume the API.
- Public contracts: The API promises the old customer field name for 90 days. Old and new clients must both work during that transition.
- Persistent production data: Customer records are retained.
- Compatibility commitments: Accept and emit both customer field names for the 90-day transition; reject requests that provide conflicting values.
- Scale and failure consequences: No scale or failure-consequence facts are known.

## Preserve

- Retained customer records.
- The 90-day API-field-name promise and service to both old and new clients during it.

## Current boundary

- The production API supports the old and new customer field names during the bounded 90-day transition. `CustomerSerializer` represents both names as one internal value.

## Ordinary paths

- Use the existing migration runner for schema changes.
- Use `CustomerSerializer` for request parsing and response serialization.
- Use its deprecation-alias facility to accept either field name, reject conflicting values, and emit both names from the one internal value during the transition.

## Proof

- Verify stored data, both API representations, rollback, and removal of old-name handling.

## Reconsider when

- Remove old-name handling only after the 90 days have elapsed and old-field traffic is zero.
