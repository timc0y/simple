# Simple

## Reality

- This is a production service.
- Published API clients depend on its API.
- Customer records are retained production data.
- The API promises the old customer field name for 90 days.
- Old and new clients must both work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Preserve retained customer records and the published API contract during the transition.
- Preserve the existing `CustomerSerializer` deprecation-alias behavior: it accepts either field name, rejects conflicting values, and emits both names from one internal value.
- Preserve the existing migration runner for schema changes.
- Preserve verification of stored data, both API representations, rollback, and removal.

## Current boundary

- `CustomerSerializer` owns customer request parsing and response serialization.
- Its deprecation-alias facility is the existing boundary for the old and new field names during the bounded transition.
- Schema changes belong to the existing migration runner.
- No broader system boundary is known from the observed facts.

## Ordinary paths

- Route customer field-name compatibility through `CustomerSerializer`.
- Use the existing migration runner for schema changes.
- Verify stored data, both API representations, rollback, and removal through the existing verification coverage.

## Proof

- Verify that stored customer data survives the schema change.
- Verify that old and new API representations work during the 90-day transition.
- Verify that conflicting field values are rejected and both names serialize from one internal value.
- Verify rollback and final removal.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero; verify that removal afterward.

## Reconsider when

- Reconsider the compatibility design if the 90-day promise, old/new client support, serializer ownership, migration runner, or zero-traffic removal condition changes.
- Establish the missing users, operators, scale, failure, security, and other compatibility facts before making decisions that depend on them.
