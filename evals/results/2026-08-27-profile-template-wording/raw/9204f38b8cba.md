# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retained customer records.
- Both old and new API clients during the 90-day transition.
- The old customer field name for the promised 90 days.

## Current boundary

- The service supports a bounded customer-field rename for its published API clients.
- The transition ends only after 90 days and zero old-field traffic.

## Ordinary paths

- Use the existing migration runner for schema changes.
- `CustomerSerializer` owns request parsing and response serialization.
- Use its existing deprecation-alias facility: it accepts either field name, rejects conflicting values, and emits both names from one internal value during the bounded transition.

## Proof

- Verify stored data, both API representations, rollback, and removal.

## Reconsider when

- Remove old-name handling only after the 90-day promise has ended and old-field traffic is zero.
