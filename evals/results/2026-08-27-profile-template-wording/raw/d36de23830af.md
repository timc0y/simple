# Simple

## Reality

- Stage and users: This is a production service used by clients through its published API. Old and new clients must both work during the transition.
- Operators: No operator, release, or support facts are known.
- External consumers: Published API clients depend on the API.
- Public contracts: The API promises the old customer field name for 90 days.
- Persistent production data: The service retains customer records, which must survive the change.
- Compatibility commitments: The old customer field name remains supported for 90 days. During that bounded transition, the existing `CustomerSerializer` deprecation-alias facility accepts either field name, rejects conflicting values, and emits both names from one internal value.
- Scale and failure consequences: No scale or failure-consequence facts are known.

## Preserve

- Preserve retained customer records.
- Preserve the published API contract for the old customer field name for 90 days.
- Preserve one internal customer value while both field names are accepted and emitted during the transition.

## Current boundary

- `CustomerSerializer` owns customer request parsing and response serialization.
- The existing deprecation-alias facility supports the old and new field names during the bounded transition.
- Schema changes use the existing migration runner.
- No other boundary, security, scale, failure, or compatibility facts are known.

## Ordinary paths

- Use `CustomerSerializer` for request parsing and response serialization, including the existing deprecation alias.
- Use the existing migration runner for schema changes.
- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.

## Proof

- Verify that stored customer data survives the schema change.
- Verify both old and new API representations during the transition.
- Verify rollback.
- Verify removal after 90 days and zero old-field traffic.

## Reconsider when

- Reconsider removal only when the 90-day API promise has elapsed and observed old-field traffic is zero.
- Reconsider the design if new facts about users, operators, scale, failure consequences, security, or compatibility obligations appear.
