# Simple

## Reality

- Stage and users: Production service used by customers through published API clients.
- Operators: Unknown.
- External consumers: Published API clients depend on the API.
- Public contracts: The API promises the old customer field name for 90 days. Old and new clients must both work during the transition.
- Persistent production data: Retained customer records must survive changes.
- Compatibility commitments: The old and new customer field names must work during the 90-day transition.
- Scale and failure consequences: Unknown.

## Preserve

- Retained customer records.
- `CustomerSerializer` ownership of request parsing and response serialization.
- Its deprecation-alias facility: it accepts either field name, rejects conflicting values, and emits both names from one internal value during a bounded transition.
- The existing migration runner.

## Current boundary

- The service supports published API clients and retained customer records.
- `CustomerSerializer` owns customer-field parsing and serialization.
- Schema changes use the existing migration runner.

## Ordinary paths

- Use `CustomerSerializer` for request parsing and response serialization.
- Use its existing deprecation-alias facility for the bounded field-name transition.
- Use the existing migration runner for schema changes.

## Proof

- Verify stored data.
- Verify both API representations.
- Verify rollback.
- Verify removal after 90 days and zero old-field traffic.

## Reconsider when

- Remove old-name handling only after 90 days have passed and old-field traffic is zero.
- Reconsider other design decisions only if new facts emerge about users, operators, scale, failure, security, or compatibility.
