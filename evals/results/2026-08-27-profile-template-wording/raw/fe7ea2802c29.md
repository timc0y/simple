# Simple

## Reality

- This is a production service with published API clients and retained customer records.
- The API promises the old customer field name for 90 days.
- Both old and new clients must work during that transition.
- No other users, operators, scale, failure, security, or compatibility facts are known.

## Preserve

- Retained customer records.
- The 90-day API promise for the old customer field name, while accepting both field names for old and new clients.
- Conflict rejection when both field names carry different values.

## Current boundary

- The API supports the old and new customer field names during the 90-day transition. `CustomerSerializer` accepts either name and emits both names from one internal value through its bounded deprecation alias.

## Ordinary paths

- Use the existing migration runner for schema changes.
- Use `CustomerSerializer` for request parsing and response serialization, including its deprecation-alias facility.

## Proof

- Verify stored data, both API representations, rollback, and removal of the old-name handling.

## Reconsider when

- Remove old-name handling only after 90 days have elapsed and old-field traffic is zero.
