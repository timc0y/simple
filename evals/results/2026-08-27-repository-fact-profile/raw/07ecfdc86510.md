Implement the rename as one bounded migration owned by the existing customer path.

1. Add a schema migration using the repository’s existing migration mechanism. Rename the persisted field from the old name to the new name, preserving every customer value. Do not maintain two stored fields or dual-write them.

2. Update `CustomerSerializer` so requests accept both the old and new API names. If both are supplied with different values, reject the request; if both match, use the single internal value.

3. During the 90-day deprecation period, serialize that value under both API names. This keeps published clients working while allowing new clients to adopt the new name.

4. Test the complete contract:

   - Existing records retain their values after migration.
   - Old-name requests and new-name requests both work.
   - Conflicting names are rejected.
   - Responses contain both names with identical values.
   - Rollback restores the schema and data without loss.
   - Migration is safe to rerun or is otherwise tracked by the normal migration system.

5. After 90 days, confirm old-client traffic is zero. Then remove the old serializer alias and old response name in a follow-up change. Keep only the renamed persisted field and new API representation.

The exact old and new field names are not present in the repository guidance, so they must be supplied from the change request before implementation.
