Implement one internal field rename with a bounded API alias.

### Design

- Rename the persisted column from `old_name` to `new_name` using the existing schema migration mechanism.
- Preserve all values; this is a column rename, not a data transformation.
- Rename the internal customer field to `new_name`.
- Extend `CustomerSerializer`’s existing deprecation-alias facility:
  - requests accept `old_name` and `new_name`;
  - conflicting values are rejected;
  - responses emit both names from the single internal `new_name` value.
- Document `old_name` as deprecated for 90 days.

There should be no second internal field, separate source of truth, permanent dual-write path, or new abstraction.

### Rollout

1. Add the reversible persisted-field rename migration.
2. Deploy the model and serializer change with both API names supported.
3. Verify existing records, reads, writes, conflict rejection, and both response names.
4. Monitor old-field traffic during the 90-day deprecation period.
5. When the period ends and old-client traffic is zero, remove the alias and old response name in a follow-up change.

### Proof and rollback

Test that:

- every existing customer value survives the migration;
- old and new request names produce the same stored value;
- conflicting names fail;
- responses contain both names during the transition;
- rollback restores the previous column/API behaviour without data loss.

The removal decision depends on the 90-day promise ending and old-client traffic reaching zero.
