Use `new_field` as the sole stored and domain representation. Rename the persisted column through the existing migration mechanism, with a reversible down migration that restores `old_field`; do not keep two stored fields or dual-write them.

At the API boundary, keep one 90-day compatibility adapter:

1. Convert old-client request payloads from `old_field` to `new_field`.
2. Serialize responses for old clients as `old_field`; serialize new clients as `new_field`.
3. Validate that a payload supplying both names either has equal values or is rejected as ambiguous.
4. Document the removal date and remove the adapter, old API schema, and down migration only after the period ends and old-client traffic is zero.

The migration must preserve every retained customer value. Verify migrated records, old and new API representations, migration rollback followed by deployment of the prior release, and the traffic-based removal criterion.

One fact is required before implementation: how the service distinguishes an old client from a new one (existing API version, media type, or another published contract). Without that discriminator, a single response cannot safely choose between two incompatible field names.
