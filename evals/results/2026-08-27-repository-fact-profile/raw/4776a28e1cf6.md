Implement a bounded compatibility migration:

1. Add a reversible schema migration using the existing migration mechanism. Rename the persisted field from `old_field` to `new_field`, preserving all values. If the database cannot safely rename it during rolling deploys, add `new_field`, backfill it, and retain a temporary storage adapter.

2. Make `new_field` the sole internal and persistence representation. Keep compatibility logic at the public API boundary.

3. For the 90-day deprecation period:

   - Accept both `oldField` and `newField` in requests.
   - If both are supplied with different values, reject the request.
   - Read and write the canonical `new_field`.
   - Return the old or new API name according to the service’s existing API-version or content-negotiation mechanism.
   - Emit deprecation warnings for use of `oldField`.

4. Monitor old-field traffic. After 90 days, remove the old request and response representation only when old-client traffic is zero or explicitly waived. Then remove the compatibility adapter and any temporary storage column or migration code.

Verify before release and during rollback that:

- Existing records retain their values.
- Old clients continue to work.
- New clients see `newField`.
- Conflicting request fields are rejected.
- The migration reverses cleanly.
- No old-client traffic remains before removal.

Do not create a permanent second field, API version, or dual-write path unless the existing deployment mechanism requires it for safe rollback.
