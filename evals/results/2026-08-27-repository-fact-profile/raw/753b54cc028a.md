Implement the rename as an expand-and-contract migration with one compatibility adapter.

### Implementation

1. Add the new persisted field through the existing migration mechanism. Keep the old field temporarily.
2. Backfill the new field from the old field and verify counts, nullability, and representative customer records.
3. Make the service’s internal model use only the new field.
4. Add a bounded API adapter:
   - accept the old and new public names;
   - map both to the new internal field;
   - return the representation required by the caller’s existing API version or negotiation mechanism.
5. Deploy this while retaining the old database field for rollback.
6. Monitor old-field API traffic and record the deprecation deadline.

During the 90-day period, old and new clients must produce the same internal value, and customer data must remain readable through both representations. Test stored data, old-client responses, new-client responses, writes through both names, and rollback to the previous service version.

After 90 days, remove the adapter only when old-client traffic is zero and the deprecation commitment has ended. Then verify the new field is complete, remove the old-field reads and writes, and drop the old persisted field in a separate migration. Keep a backup or recovery path until that migration is verified.
