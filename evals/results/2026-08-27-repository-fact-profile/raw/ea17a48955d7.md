## Implementation

Rename the persisted field through the existing schema migration mechanism, making the new field the sole stored source of truth.

During the 90-day deprecation period, keep one API compatibility adapter:

- Accept the old and new request fields.
- If both are supplied with different values, reject the request.
- Translate the old field to the new field before persistence.
- Return both representations, derived from the same new stored field.
- Mark the old representation deprecated in the API documentation.

Preserve customer data with a verified backup and a reversible migration. Do not add dual-write storage or a second schema path.

## Proof

Verify that:

- Existing records retain their values after the persisted-field rename.
- Old clients can read and write successfully.
- New clients receive and submit the renamed representation.
- Conflicting old and new inputs fail safely.
- Rollback restores the original field and API behaviour.
- Old-client traffic reaches zero after the 90-day promise ends.

Then remove the old API adapter and representation. Keep the renamed persisted field as the canonical field.
