Implementation decision: use the existing in-process runner.

Add one daily scheduled job whose handler performs the customer import. Keep scheduling and transient-failure retry policies in the runner. Make the import idempotent by using the customer’s stable external ID as the upsert key; repeated runs update the same record rather than create duplicates. Do not add a worker system or new dependency.

Proof through the runner should cover:

- Scheduling: advance the runner to the daily due time and verify exactly one import execution.
- Execution: run the scheduled job with customer data and verify records are imported.
- Retry: make the import fail transiently, verify the runner retries using its existing policy, then verify success.
- Idempotency: execute the same scheduled import twice and verify customer count and identities remain unchanged.

This is sufficient for the stated small load and preserves the current owner of scheduling and retries. Reconsider a separate execution system only after measured runner capacity or isolation requirements are exceeded.
