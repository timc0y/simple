Ship the one-shot CLI, not the daemon.

First establish that the ~180 ms is cold-process import/startup cost: measure repeated cold command latency (p50/p95), separately time remote work, and capture an import/profile trace showing the generator → compiler chain on the command path. Confirm the generated JSON is present, fresh, and produces identical command results when loaded without the generator. Measure bundling only as a comparison, not as the presumed fix.

Test the smallest change first: have the common module read or reference the already-generated JSON directly, with a small dependency-free path constant if needed. Keep generation in its existing build/generation workflow; do not load the generator or compiler at command runtime. Prove it with cold latency and existing command-behaviour/safety tests.

If that succeeds, remove the daemon prototype and its supporting machinery:

- HTTP server and service installation
- second composition root and duplicate routes
- parity tests for the parallel path
- status/recovery commands
- lazy route loader introduced solely for daemon/direct-CLI consistency

Do not ship bundling unless its measurement shows it is still needed after removing the unnecessary runtime dependency and it improves the required cold latency without adding a larger operational burden.

A resident process becomes justified only when a measured, present capability needs continuity across commands—such as maintaining a live subscription, long-lived connection, or in-memory coordination—and that continuity cannot be represented as durable completed-task data. Faster startup by itself is not that condition.
