## Implementation decision

Use the existing in-process runner:

- Register one daily customer-import job with the runner.
- Keep execution in the application process.
- Let the runner retain its current scheduling and transient-failure retry behavior.
- Make the import idempotent using the application’s existing durable customer identity and upsert/duplicate-handling path.
- Do not add a worker queue, separate scheduler, or new execution service.

Reconsider a separate execution system only after measured runner load, execution duration, concurrency, or isolation requirements exceed its capability.

## Proof

Add runner-level tests that demonstrate:

1. **Scheduling** — advancing the runner clock across the daily boundary invokes the import once; before the boundary it does not.
2. **Execution** — a scheduled invocation calls the customer-import operation and persists the expected customers.
3. **Retry** — a transient failure causes the runner’s existing retry behavior, then succeeds without introducing another retry mechanism.
4. **Idempotency** — running the same import twice, including after a retry, produces one customer per stable identity and no duplicate side effects.

This checkout contains no application source, runner implementation, persistence model, or test harness, so those proofs cannot be executed or tied to concrete symbols here. The decision is supported by the stated deployment facts: small load, an existing runner that already owns scheduling and retries, and no separate worker system.
