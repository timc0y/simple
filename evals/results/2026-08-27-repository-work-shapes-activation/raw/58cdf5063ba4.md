Ship the direct CLI with the import dependency fixed. Do not ship the resident daemon.

The evidence to establish is:

- Cold-start timing split into process startup, module loading, remote operation, and exit.
- Import graph showing the common module → generator → compiler chain.
- Confirmation that the command consumes only the generated JSON.
- Repeated subprocess benchmarks before and after, including command results, safety checks, and durable-record behavior.
- A check that the generated artifact is present and identical in development, packaging, and deployment.

Test the smallest change first: have the common module consume the generated JSON directly, or import the path from a tiny dependency-free constants module. Do not bundle yet; measure the import correction before introducing a build or packaging change.

If that removes the regression, the daemon’s compensating machinery becomes removable: the HTTP server, service installation, second composition root, duplicate route table, lazy route loader, parity tests, and service status/recovery commands. Keep the existing CLI route and durable task records. Bundling is also unnecessary unless measurement later shows a separate benefit.

A resident process becomes justified only when a measured requirement needs continuity across commands—such as retained live state, connection/session reuse, subscriptions, or a sustained workload—and that requirement cannot be represented safely as durable data or met by the one-shot path. The current facts establish startup overhead, not such a requirement.
