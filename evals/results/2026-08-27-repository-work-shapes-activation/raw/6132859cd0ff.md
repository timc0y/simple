Implement the customer import as one daily job registered with the existing in-process runner. Do not add a worker, queue, or second scheduler.

The runner remains the owner of:

- Daily scheduling, including its existing timezone/misfire behavior.
- Job execution.
- Transient-failure classification and retry timing.
- Run visibility and failure reporting.

The import handler should only fetch and persist customers. Make persistence idempotent using the source system’s stable customer identifier as the unique key and upsert key. If a retry follows a partial import, already-persisted customers are updated or skipped; no duplicate customer records are created. Do not infer deletions from a missing source record unless deletion synchronization is separately required.

Prove the behaviour through the runner’s public test surface, using its controllable clock and retry hooks rather than calling the import handler directly:

| Behaviour | Runner-level proof |
|---|---|
| Scheduling | Advance the runner to one daily boundary; assert exactly one customer-import run is dispatched. Advance to the next boundary; assert one further dispatch. |
| Execution | Dispatch the scheduled run with a known source fixture; assert the expected customers are persisted through the application’s normal storage boundary. |
| Retry | Make the source or persistence operation fail transiently once; assert the runner records the failed attempt, waits according to its existing retry policy, and completes the same scheduled run on retry. |
| Idempotency | Fail after at least one customer has been persisted, then let the runner retry. Assert one record per source customer identifier and correct final customer values. Repeat delivery of the same daily run and assert the same result. |

The only new durable rule is the customer identity uniqueness/upsert invariant; it is what makes runner retries safe across process interruption. If the application already has a customer identity constraint, reuse it rather than adding parallel import-run state.

Reconsider a separate execution system only when measurements show the in-process runner cannot meet required schedule latency, throughput, or availability, or when import isolation is required to protect the application process. The supplied workspace contains only the request prompt, not the application or runner code, so this is the implementation decision and acceptance proof rather than executed test evidence.
