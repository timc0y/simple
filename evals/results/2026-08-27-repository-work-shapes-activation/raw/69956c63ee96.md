Ship the one-shot CLI with the unnecessary import removed. Do not ship the daemon or bundling yet.

Establish evidence by measuring cold-process wall time for representative commands, split into module loading/composition, command work, remote-operation time, and exit. Capture an import trace/profile proving whether the common module’s path lookup reaches the generator and compiler. Preserve a behaviour baseline: command grammar, output/results, safety checks, and completed-record persistence.

Test the smallest change first: make the generated JSON path available without importing its generator—for example, a tiny dependency-free paths/config module—or have the consumer read the generated JSON directly from that stable path. The command needs the generated artifact; it has no stated need to load code that produces it.

Accept it if cold latency recovers the material portion of the ~180 ms regression while behaviour remains identical. If it does not, use the profile to address the next measured startup cost; measure bundling as a separate experiment, not as an assumed cure.

If it succeeds, remove the daemon prototype and its now-unneeded HTTP server, service installation/status/recovery commands, second composition root, duplicate routing, lazy route loader, and daemon/parity-only tests—after checking no retained command or operational contract depends on them. Keep the single CLI composition and route table as the owner.

A resident process becomes justified only when measurement identifies a required capability that must continue across commands and cannot be represented as durable data—for example, a necessary live session, stream, or background operation—and the one-shot path demonstrably cannot meet its latency or correctness requirement. Startup cost alone, without that requirement, does not justify a second system.
