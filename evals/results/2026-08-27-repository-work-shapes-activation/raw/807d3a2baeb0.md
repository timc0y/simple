## Implementation decision

Add the import as a daily job owned by the existing in-process runner.

- Keep scheduling in the runner.
- Keep transient-failure retries in the runner.
- Execute the existing customer import path from the scheduled job.
- Make writes idempotent using the customer’s stable external identity and the existing create/update persistence boundary.
- Do not introduce a worker queue or separate execution service.

Reconsider another execution system only after measured runner load or an explicit isolation requirement exceeds its capability.

## Proof

The required runner-level proof is:

1. **Scheduling:** advance the runner clock across the daily due time and verify one import is dispatched; verify no dispatch before it is due.
2. **Execution:** run the scheduled job through the runner and verify imported customers reach the normal customer store.
3. **Retry:** make the import fail transiently, verify the runner applies its existing retry policy, then allow success and verify completion.
4. **Idempotency:** execute the same import twice, including after a retry, and verify the customer store contains one record per stable customer identity with the expected final values.

Therefore the decision is clear from the stated constraints, but the behavioral proof cannot truthfully be claimed as executed here.
