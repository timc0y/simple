## Implementation decision

Use the existing in-process runner for a daily customer-import job.

- Register one daily schedule with the runner.
- Keep execution in the existing application process.
- Keep transient-failure retries owned by the runner.
- Make the import idempotent using the customer’s stable external identifier and an upsert/transactional write.
- Do not add a worker queue, separate service, or second retry system.

The repository contains no application source or runner implementation, so exact registration and persistence APIs cannot be specified or verified here.

## Proof through the runner

Add runner-level tests that demonstrate:

1. **Scheduling** — advancing the runner clock to the daily due time creates exactly one import execution.
2. **Execution** — the runner invokes the import and all fetched customers are persisted.
3. **Retry** — force a transient failure; the runner retries according to its existing retry policy, and a later successful attempt completes the import.
4. **Idempotency** — run the same daily import twice, or retry after partial progress; stable customer records are updated rather than duplicated, and the final state matches one successful import.

The proof should observe the runner’s public scheduling and execution surface, not call the import service directly. This preserves and verifies the runner’s existing scheduling and retry behavior.

Reconsider a separate execution system only after measured runner load, execution duration, concurrency, or isolation requirements exceed its demonstrated capability.
