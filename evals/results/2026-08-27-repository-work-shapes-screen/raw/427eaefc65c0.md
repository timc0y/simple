Add one daily `customerImport` job to the existing in-process runner. Let the job own fetching, validating, and applying the import; rely on the runner’s existing scheduling and retry behaviour.

The import must be idempotent: repeated execution of the same source data updates the same customer rather than creating duplicates. Use the source system’s stable customer identifier as the matching key, and make each accepted record an upsert in the application’s customer store.

Do not introduce a separate worker, queue, scheduler, or retry mechanism. Current load and operational boundaries do not require them.

The remaining required decisions are source-specific: where records come from, the stable identifier, field mapping and validation rules, and how malformed records are reported or quarantined. Until those are defined, there is no truthful detailed import design.

Verify through the runner’s public path: scheduled execution imports customers, a transient failure retries, and rerunning the same input leaves one correct customer record per source identifier. Reconsider a separate worker only if measured load or isolation needs exceed the runner’s capability.
