Ship the one-shot CLI. Do not ship the daemon or bundling yet.

### Evidence to establish

- Measure cold-start latency before and after the change, separating import time from the remote operation.
- Trace imports to confirm the generator pulls in the compiler and that neither is needed to read the generated JSON.
- Verify the generated JSON path, freshness, packaging, and error behaviour.
- Run existing command and safety checks, including persistence and post-exit readability of completed task records.
- Measure bundling separately if it remains a candidate; do not assume it improves startup.

### Smallest change to test first

Replace the common module’s generator import with a direct reference to the already-generated JSON, using the existing CLI composition path. Preserve command grammar, results, validation, and durable records.

If cold latency improves while behaviour remains unchanged, keep that change. The generator and compiler then become removable from this command’s runtime dependency path.

### What becomes removable

A successful direct-reference test removes the need for:

- The generator import and its compiler dependency on the CLI path.
- The resident HTTP daemon.
- Its service installation, status, and recovery commands.
- Its second composition root.
- Its duplicate route table.
- The lazy route loader.
- Daemon parity tests and other daemon-only support code.

Remove only code proven to have no remaining caller or retained-data obligation.

### When residency becomes justified

Reconsider a resident process only when a measured user or operational requirement needs continuity across commands that cannot be represented as durable data—for example, a persistent live session or connection whose reuse is necessary for a demonstrated capability. A 180 ms startup regression alone should first be addressed at its import boundary and measured again.
