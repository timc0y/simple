Ship neither the daemon nor bundling yet. First attribute the 180 ms regression with startup profiling and import timing, separating process startup, module loading, generator/compiler loading, remote-operation latency, and teardown.

Test the smallest fix: replace the runtime import of the generator with a direct import/read of the already-generated JSON (or move the path constant into a dependency-free module). Verify command output, cold-start latency, and that regeneration still works in its build step.

If that removes the material cost, delete the daemon prototype and its HTTP server, installation/service lifecycle, duplicate composition root and routes, parity tests, status/recovery commands, and lazy route loader. Avoid bundling unless measurement shows residual startup/module-resolution cost worth its build and debugging trade-offs.

A resident process is justified only if, after eliminating unnecessary startup work and measuring representative workloads, cold-start latency remains a meaningful user-facing problem and the workload has enough command frequency or latency sensitivity to repay the operational complexity and reliability burden of a daemon.
