The smallest design is one in-process job owned by the existing runner:

```text
daily schedule
  -> fetch customer pages
  -> validate each record
  -> upsert by stable external customer ID
  -> record summary
```

The job should:

- Reuse the existing scheduler and retry mechanism.
- Process the complete source from the beginning on each run.
- Upsert customers using a stable source identifier, making retries and reruns idempotent.
- Validate records at the import boundary and reject malformed records without corrupting stored data.
- Treat a run as failed if the source cannot be read or required records cannot be persisted.
- Log counts for read, created, updated, rejected, and failed records.
- Avoid deleting local customers unless deletion semantics are explicitly required.
- Avoid a worker service, queue, cursor store, or new dependency at the current scale.

A retry can safely restart the import because each successful record is written by its stable external ID. If the source supports only non-repeatable pagination, establish a resumable cursor before implementation; otherwise, cursor state is unnecessary.

Required facts before coding:

- Source system and authentication method.
- Destination customer model and required fields.
- Stable customer identity and conflict rules.
- Whether source deletions must be reflected locally.
- Required daily execution time and timezone.
- Expected volume and acceptable run duration.

Proof should exercise the runner’s public surface: scheduled execution, successful import, transient retry, rerun without duplicates, malformed-record handling, and a failure midway through the import. Reconsider the design only when measured volume or isolation requirements exceed the in-process runner’s capability.
