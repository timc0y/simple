Run one in-process `CustomerImport` job through the existing runner’s daily schedule and retry mechanism.

Its invariant: retrying the same source data produces the same customer state, without duplicate customers or deletion of customers absent from the import.

The job should:

1. Fetch that day’s customer input.
2. Validate required identifiers and fields before writing.
3. Upsert each customer using the source system’s stable customer ID as the idempotency key.
4. Treat an incomplete fetch, invalid required data, or failed write as a job failure so the runner retries it.
5. Record enough job-level outcome data to diagnose the run: source version/date if available, counts imported/rejected, and the failure reason.

Keep the import logic inside the scheduled job; do not add a worker service, queue, or separate retry workflow. The existing runner remains the owner of scheduling and retries.

Do not infer deletion from an absent record unless the source contract explicitly says each import is a complete authoritative snapshot. If the source does not provide a stable customer ID or a way to identify the input version, establish that contract first: idempotency cannot be proved otherwise.

Verify through the runner that the job is scheduled, imports a valid input, retries a transient failure, and can run the identical input twice without changing the resulting customer set. Revisit the in-process design only when measured load or required isolation exceeds the runner’s capability.
