Design a single in-process `CustomerImport` job owned by the existing runner.

```text
Daily schedule
  → fetch the source customer records
  → validate and map each record
  → upsert by stable source customer ID
  → report imported, updated, skipped, and failed counts
```

The runner remains responsible for scheduling and retrying. The import job should:

- Use the source’s stable customer ID as the idempotency key.
- Make retries safe through deterministic upserts; rerunning a completed day must not create duplicates.
- Validate records at the import boundary before writing them.
- Treat source or infrastructure failures as job failures so the existing retry behaviour applies.
- Avoid deleting or deactivating customers absent from an import unless the source contract explicitly requires that.
- Keep execution in-process; no worker system, queue, or new framework is justified at the current load.

The required boundary is:

```text
CustomerImport.run()
```

It owns source retrieval, validation, mapping, and persistence. The runner knows only when to invoke it and whether it succeeded.

Proof should run through the existing runner:

1. The job runs on the daily schedule.
2. A successful run persists new and changed customers.
3. A transient failure is retried.
4. Repeating the same run produces no duplicates or unintended changes.

Before implementation, establish the source format, authentication method, stable identifier, update semantics, and whether invalid records should fail the whole import or be skipped and reported. Reconsider this design only when measured load or isolation requirements exceed the in-process runner’s capability.
