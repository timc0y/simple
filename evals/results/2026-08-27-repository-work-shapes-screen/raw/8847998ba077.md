Ship the one-shot CLI. Do not ship the resident daemon for a startup regression that has not been tied to a required operation.

### Evidence to establish

- Measure cold-start latency before and after the dependency change, separating process startup, module loading, remote work, and shutdown.
- Trace the import graph to confirm that the common module reaches the compiler only through the generator.
- Confirm that the generated JSON is a stable, available artifact with the required contents and lifecycle.
- Run the existing command suite, including safety checks and durable task-record reads, to prove behaviour is unchanged.

### Smallest change to test first

Change the common module to consume the generated JSON directly, or use the existing generated artifact’s path directly, instead of importing the generator. This should remove the generator-to-compiler import chain while preserving the existing CLI composition root and route table.

Then compare cold command latency and command results on the same representative commands.

### What becomes removable

If the direct dependency change removes the regression and behaviour remains correct, remove the unshipped daemon machinery:

- HTTP server and service installation
- second composition root
- duplicate route table
- lazy route loader added for parity
- daemon parity tests
- service status and recovery commands

Keep the ordinary CLI path and durable completed task records.

### When residency becomes justified

Reconsider a resident process only when a measured capability requires continuity across commands and cannot be represented as durable data—for example, persistent connection/session state, subscriptions, batching, or a required warm cache—and the one-shot CLI cannot provide that capability within an acceptable measured latency.
