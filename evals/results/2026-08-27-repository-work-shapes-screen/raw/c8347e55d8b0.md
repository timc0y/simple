Ship the simplest direct CLI for now. The daemon adds substantial operational and maintenance cost without evidence that startup is the required bottleneck.

Establish:

- A benchmark separating process startup, module loading, generator/compiler imports, remote I/O, serialization, and command execution.
- Repeated cold and warm measurements, with variance, across representative commands.
- An import/dependency trace confirming whether the generator and compiler are loaded only to obtain a path constant.
- A correctness test proving the CLI can consume the generated JSON directly and that generation remains part of the build/release step.
- A comparison of the proposed bundling approach against the current 180 ms regression.

Test first: replace the runtime import of the generator with a direct import of the generated JSON or a small checked-in path-constants module. Keep the change local, benchmark it, and verify behavior and packaging.

If this removes the slowdown, the generator and compiler no longer belong in the command’s runtime dependency path. The daemon, HTTP server, second composition root, duplicate route table, lazy loader, service installation, status/recovery commands, and parity-test infrastructure can all be removed unless they serve an independent requirement.

A resident process becomes justified only if measured command latency remains materially unacceptable after removing avoidable startup work, and a daemon demonstrably improves the relevant workload enough to outweigh its deployment, recovery, compatibility, and maintenance costs. That case should be supported by production-like benchmarks showing repeated commands where keeping a process alive saves substantial time and the operational environment can reliably supervise it.
