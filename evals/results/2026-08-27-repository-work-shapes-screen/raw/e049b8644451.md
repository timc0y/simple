# Daily customer import

Run one `customer-import` job through the existing runner once per day. Keep execution in-process and preserve the runner’s current scheduling and retry behavior.

## Design

1. The runner starts the import job daily.
2. The job reads customers from the existing source using its supported API or file interface.
3. It validates required fields at the import boundary.
4. It upserts each customer into the existing customer store using the source’s stable customer ID as the idempotency key.
5. It records the import result: processed, created, updated, rejected, and failed.
6. It returns transient failures to the runner so they can be retried. Invalid customer data is reported as rejected and is not retried.

The customer store remains the source of truth for application reads. The import job owns only source retrieval, validation, and synchronization.

## Required contract

```text
Customer {
  source_id: stable required identifier
  name: required
  email: required and valid
  updated_at: source modification time
}
```

The exact source, destination schema, schedule time, and conflict rules remain unknown and must be confirmed before implementation. In particular, decide whether source deletions should delete customers, deactivate them, or be ignored.

## Proof

Use the existing runner to verify:

- the job runs on its daily schedule;
- a new customer is created;
- an existing `source_id` is updated rather than duplicated;
- rerunning the same import produces no additional changes;
- transient source failure is retried;
- invalid records are rejected without retrying the whole import.

No separate worker, queue, service, or custom scheduler is required at the current scale. Reconsider that boundary only when measured load or isolation requirements exceed the existing runner.
