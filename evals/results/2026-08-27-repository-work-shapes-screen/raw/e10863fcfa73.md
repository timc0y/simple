## Daily customer import design

- Schedule one `customer-import` job daily through the existing runner, preferably after the source system’s daily export is complete.
- Keep execution in-process; no separate worker system is needed at the current scale.
- Give each run a key such as `(source, import_date)` and record its status: `started`, `completed`, or `failed`.
- Read customers from the source, validate required fields, then upsert using the source’s immutable customer ID.
- Process in batches so transient failures can retry without repeating completed work.
- Make writes idempotent: rerunning the same date must produce the same records and must not create duplicates. Use source version or `updated_at` to prevent stale data overwriting newer data.
- Commit each batch transactionally. Record batch progress or source cursor only after its database write succeeds.
- Treat authentication, malformed input, and schema errors as non-retryable and alert the application team. Retry network errors, timeouts, and rate limits using the runner’s existing retry behavior.
- Mark the run complete only after the full source has been consumed and required reconciliation checks pass.
- Emit metrics and logs for run duration, records read/created/updated/rejected, retries, and final status.

## Verification

Use the existing runner to verify:

1. The job runs once per day.
2. A successful run imports and updates the expected customers.
3. A transient failure retries and resumes safely.
4. Re-running the same import does not duplicate or corrupt data.
5. Invalid records are reported without causing endless retries.

Reconsider this design if measured volume, execution time, or isolation requirements exceed what the in-process runner can support.
