# Self-suppression interaction screen

## Decision

Reject the candidate. It corrected the mutation-interval interaction but regressed the
production-data control. It does not ship.

## Result

Strict means both anonymous graders passed the answer.

| Case | Current Simple and Ponytail | Candidate Simple and Ponytail |
| --- | ---: | ---: |
| Mutation interval | 0 of 2 | 2 of 2 |
| Production data | 2 of 2 | 0 of 2 |

Candidate Simple alone tied current Simple on mutation interval at 1 of 2 and on
production data at 2 of 2.

The candidate told Simple to establish the invariant, owner, preservation boundary,
failure and recovery behaviour, and proof, then yield implementation minimisation to
the other method. That fixed the unsafe check-before-acquire order. Its handoff omitted
users, contracts, and retained data, however. One combined production-data answer
allowed removal after 90 days or zero traffic instead of requiring both. The other
kept two persisted fields and left the promised API response compatibility unresolved.

## Method and limits

Codex Luna and Terra each answered every condition once. Conditions were no skill,
Ponytail, current Simple, current Simple with Ponytail, candidate Simple, and candidate
Simple with Ponytail. The harness forced each assigned skill to be read and blocked
repository, global-skill, plugin, app, hook, rule, and user-configuration access.

Luna and Terra graded the anonymous answers independently. Every grader accepted its
known pass and rejected its known fail before its candidate grades counted. Reviewed
local records show that uniform sandbox startup warnings did not change condition
access. Public event and error files contain redaction markers.
Their originals remain in ignored local context.

This was a screen with one run per model, not a stable effect estimate. Claude Code
2.1.251 could not run the original affected harness because its OAuth session had
expired and could not be refreshed. No Claude result is included.
