The proposal should add `summary` to the existing event, not replace the structured fields:

```json
{
  "actor": "...",
  "action": "...",
  "target": "...",
  "retention_days": 30,
  "summary": "..."
}
```

`actor`, `action`, `target`, and `retention_days` remain canonical, queryable data. `summary` is an additional human-readable projection; it must not become the source from which those fields are reconstructed.

The event schema remains owned by the service team. The service updates its event writer to populate `summary`, while the incident tool continues consuming the structured record and may render the new field. Retention enforcement continues to read `retention_days`. Existing incident-tool queries remain unchanged.

The smallest change is:

1. Extend the existing schema with `summary`.
2. Update the service writer to store it.
3. Update the incident tool to display it where useful.
4. Preserve existing validation, queries, and retention handling.

Proof:

- Write an event containing all five fields.
- Query `actor`, `action`, `target`, and `retention_days` individually.
- Verify the incident tool renders `summary`.
- Verify retention enforcement still uses `retention_days`.
- Verify existing events and queries retain their current behaviour.
