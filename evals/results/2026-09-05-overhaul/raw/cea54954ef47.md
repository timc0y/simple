The proposal should extend the existing audit event, not replace it:

```json
{
  "actor": "...",
  "action": "...",
  "target": "...",
  "retention_days": 30,
  "summary": "..."
}
```

`actor`, `action`, `target`, and `retention_days` remain structured, queryable, authoritative fields. `summary` is an additional human-readable representation; it must not be used to reconstruct the original data.

The service team owns the schema, migration, and event writer. The incident tool remains a consumer: it reads the structured fields for queries and retention-related behaviour, and renders `summary` for people.

The smallest change is to add `summary` to the existing schema and update the writer and reader. Existing records can receive a compatibility default or be backfilled; retention enforcement remains unchanged and continues to use `retention_days`.

Proof:

- Write an event containing all five fields.
- Query and verify each existing field independently.
- Render and verify `summary`.
- Confirm existing incident-tool queries still pass.
- Confirm retention enforcement still uses `retention_days`.
- Verify old records remain readable during and after migration.
