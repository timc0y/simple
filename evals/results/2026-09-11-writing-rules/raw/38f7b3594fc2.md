# Plan

## Outcome

Add a monthly usage CSV export that finance can import by the existing column headers, while preserving the old report’s 14-column structure, two empty legacy columns, `Total` footer row, and Windows line endings.

The old file does not need to remain byte-for-byte identical: no downstream job, published API, or retained data depends on its bytes, and finance does not compare files between months.

## Relevant facts

- The retired script defined the old 14-column layout.
- the consumer is the only consumer and imports by column header name.
- The application already owns CSV generation through a writer used by two exports.
- That writer currently emits only a header row and data rows.
- Exact byte compatibility would require a second formatter, a legacy column map, and a fixture.
- The request’s byte-identical constraint is stricter than the demonstrated consumer requirement.

## Preserved behaviour

Preserve:

- The 14 column positions and names.
- Both empty legacy columns.
- The `Total` footer row.
- Windows line endings.
- CSV escaping and quoting rules required by the existing writer.
- Monthly usage values and totals.

The retired script, byte-for-byte output, and separate formatter may be replaced because no consumer depends on them.

## Smallest design

Extend the existing CSV export path so this report supplies:

1. Its explicit 14-column schema, including the empty legacy columns.
2. Its total row as a report-specific footer.
3. Windows line-ending configuration.

Keep the existing writer as the sole CSV implementation. Do not add a second formatter or a general legacy compatibility layer.

## Implementation steps

1. Add the monthly usage report using the existing CSV writer.
2. Define the report’s 14 columns explicitly and populate the two legacy columns with empty values.
3. Add the `Total` footer through the smallest writer extension that supports report-specific footer rows without changing the two existing exports.
4. Configure this export to emit Windows line endings.
5. Add a fixture covering the header, column count, empty legacy columns, data rows, footer, escaping, and line endings.
6. Verify that the two existing CSV exports remain unchanged.

## Proof

Use two independent checks:

- Parse the generated CSV and verify the headers, 14-column shape, empty legacy fields, data values, and total row.
- Compare the generated text fixture for the required line endings and row order.

Also run the existing export tests to prove the shared writer change did not alter current consumers.

## Decision required

If “identical” means byte-for-byte compatibility despite the absence of a byte-level consumer, the plan must instead retain the old formatting rules exactly, add the legacy column map, and freeze the complete output with a fixture. That adds a second formatter and maintenance cost without serving a known obligation.

The recommended interpretation is semantic compatibility for finance’s import contract. Reconsider byte-for-byte compatibility only if finance later requires month-to-month file comparison or another consumer is found that depends on exact bytes.
