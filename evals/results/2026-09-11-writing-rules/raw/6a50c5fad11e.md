# Plan

## Outcome

Add a monthly usage report export that remains compatible with the retired report. The generated file must preserve:

- The fixed 14-column layout.
- The two empty legacy columns.
- The `Total` footer row.
- Windows line endings.
- The existing column positions consumed by the nightly reconciliation job.

The existing CSV writer cannot satisfy these requirements because it emits only headers and data rows.

## Design

Keep the existing CSV writer for the two exports that already use it. Add one bounded legacy formatter for this report, owned by the monthly usage report export.

The formatter should:

1. Map report fields to the legacy 14-column order.
2. Emit both empty legacy columns in their original positions.
3. Emit the `Total` footer row in the original shape.
4. Write Windows line endings consistently.
5. Preserve the old report’s quoting, escaping, encoding, and final-newline behaviour.

Do not add a second data model, dual writes, or a general-purpose compatibility layer. The second formatter exists for one confirmed external consumer and can be removed only when that consumer no longer requires the legacy layout.

## Implementation steps

1. Recover the retired script, an archived report, or another authoritative sample to establish the exact byte-level format, including field order, quoting, encoding, footer values, and final newline behaviour.

2. Trace the current monthly usage report path and identify the existing owner that supplies report rows and totals.

3. Add the legacy column map and formatter at the export boundary. Keep report calculation separate from legacy file formatting.

4. Add a fixture containing representative data, including values that exercise CSV quoting and the two empty columns.

5. Add a byte-level golden test that verifies the complete file, including CRLF line endings and the `Total` footer.

6. Add structural assertions that independently verify 14 columns on every relevant row and the required positions of the empty columns.

7. Verify that the normal report data and totals are unchanged before formatting.

8. Produce a sample file and have the reconciliation job owner validate it against the previous report format before release.

## Complexity avoided

- The shared CSV writer remains unchanged for consumers that do not need legacy behaviour.
- No duplicate report calculations or stored representations are introduced.
- No feature flag, versioned export, dual output, or permanent migration workflow is needed.
- The compatibility logic is isolated to the one file contract that has a confirmed downstream consumer.

## Proof and risks

The export is acceptable when the golden fixture matches the authoritative old output byte for byte, the structural tests confirm the 14-column contract, and the reconciliation job accepts the generated file.

If the retired script or an authoritative sample cannot be recovered, byte-for-byte compatibility is not provable. Pause implementation at that point and obtain the missing source of truth rather than inferring the legacy format.
