# CSV export plan

## Outcome

Add a monthly usage-report export whose bytes match the retired report’s contract:

- 14 columns in the existing order
- two empty legacy columns
- the `Total` footer row
- Windows line endings
- the same field formatting, quoting, and column positions

The nightly reconciliation job must continue reading the file without changes or operator intervention.

## Preserved behaviour

Preserve the retired report’s file layout as the compatibility contract. The application’s existing CSV writer must remain unchanged for the two exports that already use it.

The application should own generation of the new report. The reconciliation job remains the downstream consumer and source of the column-position requirement.

## Design

Add a dedicated legacy-report formatter beside the existing CSV export path.

Reuse the existing CSV writer’s low-level escaping and quoting behaviour where compatible, but supply the legacy formatter with:

- an explicit 14-column map;
- values for the two empty legacy columns;
- Windows line-ending configuration;
- the `Total` footer row;
- the legacy field and number formatting rules.

Keep the formatter’s output contract separate from the newer header-and-data-row format so changes to the existing exports cannot alter the legacy file.

## Implementation steps

1. Locate the current monthly usage-report data source and export entry point. Confirm the output filename, destination, scheduling path, and ownership.
2. Capture the retired report as the golden fixture, including its exact bytes and representative data.
3. Define the 14-column legacy map in one place, including the two deliberately empty columns.
4. Implement the dedicated formatter using the existing CSV writer’s escaping primitives where they preserve the old output.
5. Emit rows with Windows line endings and append the `Total` footer exactly as the fixture specifies.
6. Connect the monthly export entry point to the new formatter without changing the two existing exports.
7. Add tests that compare generated output byte-for-byte with the fixture.
8. Add focused assertions for column count and positions, empty legacy columns, footer placement, line endings, quoting, and total values.
9. Run the export through its normal application entry point and verify the produced file, not only the formatter in isolation.

## Proof

The golden-fixture test must fail if any of these change:

- column order or count;
- empty legacy-column positions;
- header or data formatting;
- quoting or escaping;
- line endings;
- footer text, position, or values.

A separate structural test should parse each non-footer row by position and confirm the 14-column contract. This provides useful failure messages while the byte comparison protects exact compatibility.

The final check should compare a newly generated file with the retired report fixture and confirm that the reconciliation job’s expected column positions remain unchanged.

## Complexity and cleanup

Do not change the shared writer’s default format, add a second stored report representation, or modify the reconciliation job. The dedicated formatter is necessary because the existing writer has no footer and does not represent the legacy columns or line endings.

Keep the compatibility map and fixture as the durable owners of the legacy contract. Remove any temporary comparison scripts or notes once their useful evidence is covered by the fixture and tests.

## Risks and unknowns

The repository facts do not identify the report’s current application entry point, output path, filename, or complete field-formatting rules. Establish those before implementation by inspecting the retired fixture and the existing export wiring.

Reconsider the design only if the old report contains behaviour that cannot be represented by the existing writer’s escaping rules. In that case, document the exact mismatch and add the smallest formatter-specific handling required to preserve the bytes.
