# Plan

## Outcome

Produce a monthly usage CSV that the consumer can import without changes. Preserve the old report’s 14-column header names and order if those are required by the spreadsheet.

Byte-for-byte reproduction is not currently justified: the consumer imports by header name, does not compare months, and no published interface, downstream job, or retained data depends on the file bytes.

## Decision needed

The request says “identical,” which could mean either:

1. **Import-compatible:** preserve the headers and column mapping. Use the existing CSV writer and avoid reproducing the legacy footer, empty columns, and Windows line endings unless the consumer confirms they matter.
2. **Byte-identical:** add a dedicated legacy formatter, explicit mapping for all 14 columns, the two empty columns, the `Total` footer row, Windows line endings, and a fixture containing the expected output.

The first option is the smallest truthful design. Confirm that the consumer means byte identity before choosing the second.

## Implementation steps

1. Record the old report’s header names and column order as the export contract.
2. Map the monthly usage data to that contract through the existing CSV export path.
3. Preserve the two legacy columns only if their positions or headers are required for the consumer's import.
4. Add focused tests for header names, order, and representative imported values.
5. If byte identity is confirmed, implement the bounded legacy formatter and fixture, then verify line endings, empty columns, footer content, and final column count.

## Proof

Use an independent CSV parser or the consumer's import process to verify that:

- all expected headers are present;
- each value lands under the expected header;
- the monthly report imports successfully.

For the byte-identical option, compare generated output against the frozen fixture, including line endings and the footer row.

## Complexity and risks

The semantic-compatible option avoids a second formatter and freezes only the contract the consumer consumes. The byte-identical option is appropriate only if the consumer identifies a byte-sensitive dependency or explicitly requires the legacy layout.

Reconsider the simpler option if the consumer later reports dependence on the footer, blank columns, Windows line endings, or exact file bytes.
