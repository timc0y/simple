# Plan: add a compatible CSV export

## Outcome

Add a monthly usage report export that remains byte-compatible with the retired report. The reconciliation job must continue reading the file by column position and comparing it with the previous month without changes.

## Preserve

- The fixed 14-column layout.
- Both empty legacy columns, in their existing positions.
- The `Total` footer row.
- Windows line endings.
- Existing field ordering, quoting, and value formatting.
- The reconciliation job’s expected filename and file structure, if those are still part of the report contract.

## Design

Use a dedicated legacy-report formatter for this export. Do not route it through the shared CSV writer because that writer cannot emit the required footer and does not preserve the legacy layout.

The formatter should:

1. Map application data to the exact 14-column legacy order.
2. Insert the two empty legacy columns explicitly.
3. Write the header and data rows using the existing CSV escaping rules where compatible.
4. Append the `Total` footer row in the legacy position and format.
5. Emit Windows line endings.
6. Produce the existing report file through the application’s normal report-generation path.

Keep the application’s shared CSV writer unchanged for the two exports that already use it.

## Implementation steps

1. Locate the current monthly usage report owner and its normal generation path.
2. Recover the retired script’s exact header, column order, empty-column positions, footer values, quoting rules, and line-ending behaviour from its history or retained fixtures.
3. Add the legacy column map and dedicated formatter beside the report owner.
4. Connect the monthly export to that formatter through the existing report-generation path.
5. Add a fixture containing representative data, empty legacy columns, totals, and the expected Windows-formatted output.
6. Add tests that compare the generated file with the fixture and verify column positions, footer placement, and line endings.
7. Run the reconciliation job, or an equivalent consumer-level check, against consecutive generated monthly files to confirm unchanged layout and expected comparison behaviour.

## Proof

The formatter test proves the exact file structure. An independent check should read the generated file by position, as the reconciliation job does, and verify:

- 14 columns in every header and data row.
- Empty legacy columns remain empty and correctly positioned.
- The footer is present and last.
- Line endings are `CRLF`.
- Two otherwise equivalent monthly reports produce no layout-change alert.

## Complexity and risks

The second formatter, legacy map, and fixture are required compatibility machinery, not general CSV abstractions. They encode the external consumer’s fixed contract.

Do not remove the legacy formatter or empty columns until the reconciliation job owner confirms that the consumer has been changed or retired. Reconsider the dedicated formatter only if the shared writer gains explicit support for all legacy requirements without changing the existing exports.
