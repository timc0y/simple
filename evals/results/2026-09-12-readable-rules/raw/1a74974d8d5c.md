# Plan

## Outcome

Add a monthly usage CSV export whose output remains compatible with the retired report:

- Fixed 14-column layout.
- Two empty legacy columns in their original positions.
- `Total` footer row.
- Windows line endings.
- Same header, field order, quoting, and value formatting as the old report.

The nightly reconciliation job must continue to read the file by column position without changes.

## Relevant facts

The application’s existing CSV writer is the ordinary export path, but it emits only a header row and data rows. It cannot produce the legacy footer and layout without changing the contract of the two existing exports.

The external reconciliation job is a real downstream consumer. Its owner cannot update it this quarter, so the old file format is a load-bearing compatibility requirement.

## Smallest design

Keep the application’s existing report/export owner and data source. Add a bounded legacy formatter for this report only:

1. Map the monthly report fields into the old 14-column order.
2. Emit the two legacy columns as empty values.
3. Append the `Total` footer row in the old position and format.
4. Configure Windows line endings.
5. Reuse the existing CSV escaping and quoting behavior where it matches the old output.

Do not alter the shared CSV writer’s output contract or add footer behavior to the other exports. The second formatter is justified because the existing writer cannot satisfy the retained external file contract.

## Implementation steps

1. Confirm the monthly report’s current owner and ordinary export path.
2. Capture the retired script’s exact header, column positions, empty-column locations, footer values, quoting rules, newline behavior, and numeric/date formatting in a legacy column map.
3. Implement the report-specific formatter behind the monthly usage export.
4. Keep the shared CSV writer unchanged unless its escaping behavior is required by the legacy format and can be extended without changing existing outputs.
5. Add a fixture containing a representative monthly report and the expected legacy CSV, including empty columns, the `Total` row, and Windows line endings.
6. Wire the monthly export to the formatter and ensure existing exports still use their current path.

## Proof

Verify independently that the generated file:

- Has exactly 14 columns on every header, data, and footer row.
- Places both empty legacy columns correctly.
- Includes one correctly formatted `Total` footer row.
- Uses Windows line endings throughout.
- Matches the legacy fixture byte for byte.
- Remains readable by a positional 14-column parser.
- Leaves the two existing CSV exports unchanged.

The fixture must fail if a column moves, an empty legacy column is removed or populated, the footer disappears, or line endings change.

## Complexity and boundaries

This adds one legacy formatter, one column map, and one compatibility fixture. That complexity pays for the existing downstream contract and avoids changing a shared writer used by unrelated exports.

Do not add versioning, dual output formats, a migration, or changes in the reconciliation repository. Reconsider the formatter only when the reconciliation job no longer depends on the legacy layout and its owner confirms that the compatibility contract can be retired.
