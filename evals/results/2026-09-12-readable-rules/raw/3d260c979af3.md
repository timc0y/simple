# Plan

## Outcome

Add a monthly usage CSV export that remains compatible with finance’s spreadsheet import.

“Identical” needs one decision before implementation:

- If it means identical to the retired file byte-for-byte, preserve the 14 columns, two empty legacy columns, `Total` footer row, and Windows line endings.
- If it means unchanged finance-team behavior, use the existing CSV writer with the same column headers. The footer, empty legacy columns, and line endings are unnecessary because finance imports by header name and nobody compares files between months.

The second interpretation is the smallest design supported by the known consumers. Confirm which meaning is required before implementation.

## Preserved behaviour

In either case:

- The monthly usage data and existing column header names.
- Finance’s ability to import by column header.
- The application’s existing CSV export ownership and ordinary path.

No published API, downstream job, or retained file-byte contract needs preservation.

## Implementation

If finance compatibility is sufficient:

1. Add the monthly usage report to the existing export path.
2. Reuse the current CSV writer and its established escaping and line-ending behavior.
3. Emit the required headers and usage data rows.
4. Do not add legacy columns or a footer unless finance’s import proves they are required.

If byte-for-byte legacy compatibility is explicitly required:

1. Add a narrowly scoped legacy formatter beside the existing writer.
2. Define the fixed 14-column map, including both empty legacy columns.
3. Emit the `Total` footer row.
4. Configure Windows line endings.
5. Keep the formatter specific to this report; do not change the shared writer for one legacy format.

## Proof

Test through the export’s public entry point with representative monthly data.

Verify:

- Header names and data values match the required contract.
- Finance’s spreadsheet imports each column into the expected field.
- The compatibility version contains exactly 14 columns, empty legacy columns, the `Total` row, and Windows line endings.
- The ordinary exports using the shared writer remain unchanged.

A fixture is necessary only for the byte-for-byte branch. For the finance-compatible branch, assert the headers, imported values, and absence of unintended data changes.

## Complexity and risks

Reusing the existing writer avoids a second formatter, legacy column map, footer logic, and byte-preserving fixture. The risk is that “identical” was intended literally rather than as consumer compatibility.

Use the legacy formatter only if finance or another newly identified contract requires exact file structure. That requirement would be the reconsideration condition; without it, the existing writer is sufficient.
