## Outcome

Add the monthly usage report as a CSV export that finance can import using the existing column headers and data meanings.

“Identical” should mean import-compatible, not byte-for-byte identical. The old file’s empty legacy columns, `Total` footer, and Windows line endings have no known consumer requirement behind them. Finance imports by header name and does not compare monthly files.

## Relevant facts

- The retired report used 14 columns, including two empty legacy columns.
- It ended with a `Total` footer row and Windows line endings.
- Finance is the only consumer and imports by column header name.
- The application already owns a CSV writer used by two other exports.
- That writer emits headers and data rows without a footer.
- No API, downstream job, retained data, or file-byte contract requires the old representation.

## Preserved behaviour

Preserve:

- The finance-facing column headers.
- The meaning and values of each usage field.
- Correct CSV escaping and a header row.
- The monthly report’s existing totals as data, if they are part of the report data.

Do not preserve solely for historical appearance:

- The two empty legacy columns.
- The separate `Total` footer row.
- Windows line endings.
- Byte-for-byte formatting.

If “identical” is intended to require all of those details despite the confirmed consumer behaviour, that is a different requirement and needs explicit confirmation before implementation.

## Plan

1. Identify the monthly report’s current data-producing owner and map its fields to the existing CSV writer’s column-header interface.

2. Define the export’s column headers from the old report’s finance-facing headers. Keep the names stable because they are the consumer’s import contract.

3. Reuse the existing CSV writer and its ordinary header-and-data-row path. Do not add a second formatter, legacy column map, footer mode, or line-ending option.

4. Add the monthly export entry point alongside the two existing CSV exports, keeping report generation and CSV serialization under their current owners.

5. Add a fixture or focused export test that proves:

   - the expected headers are present;
   - representative monthly data values are mapped correctly;
   - fields containing commas, quotes, or line breaks are escaped correctly;
   - no accidental legacy columns or footer row are emitted.

6. Verify the resulting file through the finance import path, or an equivalent import check that resolves fields by header name rather than comparing raw bytes.

## Complexity avoided

This avoids owning a second formatter, a permanent legacy-layout map, special footer handling, and a fixture that freezes output details no supported consumer needs.

## Risk and reconsideration

The plan must change if finance later confirms that its spreadsheet requires positional 14-column input, the empty columns, the footer row, or Windows line endings. In that case, preserve those details in a bounded compatibility formatter and prove them with a golden fixture.
