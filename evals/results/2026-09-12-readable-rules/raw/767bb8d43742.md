# Plan

## Outcome

Add a monthly usage CSV export that remains byte-for-byte compatible with the retired report. The nightly reconciliation job must continue reading the same 14 column positions and detecting changes correctly.

## Preserve

- The fixed 14-column layout.
- Both empty legacy columns, in their existing positions.
- The `Total` footer row.
- Windows line endings (`CRLF`).
- Existing field ordering, quoting, and value formatting from the retired report.
- The file location and naming contract, if those are already defined by the export interface.

The application’s existing CSV writer cannot satisfy this contract because it produces only a header row and data rows.

## Design

Keep the application’s existing report data generation and export ownership. Add a bounded legacy formatter at the CSV output boundary:

1. Define an explicit 14-column legacy column map, including the two empty columns.
2. Format the header and data rows using that map.
3. Append the `Total` footer row in the retired report’s position and format.
4. Emit `CRLF` line endings.
5. Use the existing CSV escaping rules where they match the old report; preserve any legacy-specific formatting needed for byte compatibility.

Do not change the shared CSV writer for the other exports. Their no-footer format is a different contract.

## Implementation steps

1. Recover the retired report’s exact header, column order, empty-column positions, footer values, quoting, encoding, and line-ending behaviour from the existing file or its fixture.
2. Add the legacy column map and formatter beside the monthly usage export.
3. Connect the monthly export to this formatter while retaining the application’s existing report calculations.
4. Add a golden fixture containing a representative complete report, including the empty columns, `Total` row, and `CRLF` endings.
5. Add focused checks that verify:
   - every row has exactly 14 columns;
   - both legacy columns remain empty and in the correct positions;
   - the footer is present and correctly positioned;
   - output uses `CRLF`;
   - generated output matches the fixture byte for byte;
   - ordinary values requiring CSV quoting remain compatible.

## Proof

The fixture comparison is the primary compatibility check because the downstream job depends on file bytes and column positions, not merely parsed values. Also compare a generated file with the previous month’s known-good file using the same column-position assumptions as the reconciliation job.

The export is complete only when the generated fixture is byte-identical and the 14-column and footer checks pass.

## Complexity avoided

- No change to the nightly reconciliation job.
- No modification to the shared writer used by unrelated exports.
- No duplicate report calculation or second data source.
- No versioned format, dual output, migration, or permanent compatibility layer beyond this explicitly required legacy formatter.

## Risk and reconsideration

The main risk is that the retired script’s exact quoting, encoding, or footer details are not fully recoverable from the known facts. Do not implement until those details are established from the old file or an authoritative fixture.

Reconsider the separate formatter only if the downstream job is retired or its owner accepts a format change. Until then, the external consumer and its fixed positional contract make byte-compatible output a required obligation, not an optional improvement.
