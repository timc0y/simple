# Plan

## Outcome

Add a monthly usage CSV export whose output remains compatible with the retired report:

- 14 columns in the original positional order.
- Both empty legacy columns preserved.
- The original `Total` footer row preserved.
- Windows line endings preserved.
- Existing exports remain unchanged.

The nightly reconciliation job is a real downstream consumer, so this compatibility requirement is load-bearing.

## Design

Keep the application’s existing CSV writer for its two current exports. It emits a header and data rows, so changing it to support the legacy footer, empty columns, and Windows line endings could alter existing output.

Add a dedicated legacy formatter at the monthly usage export boundary. It should:

1. Receive the monthly usage data from the existing report/data owner.
2. Map values into the fixed 14-column legacy order.
3. Insert the two empty legacy columns.
4. Write the header and data rows.
5. Append the `Total` footer row.
6. Emit Windows line endings consistently.

The legacy column map and formatting rules should remain owned by this formatter. Do not create a second data source or dual-write report state.

## Implementation steps

1. Identify the existing monthly usage report data path and make it the source for the new export.
2. Recover or confirm the authoritative legacy header, column order, empty-column positions, footer format, quoting rules, and encoding from the retired report or a known-good output file.
3. Add the legacy column map and dedicated formatter.
4. Add the export entry point using the existing monthly report flow.
5. Keep the shared CSV writer unchanged unless inspection proves it can support the legacy contract without changing either existing export.
6. Add a byte-for-byte fixture based on the authoritative legacy output. The fixture must cover:
   - all 14 columns;
   - both empty legacy columns;
   - the `Total` footer;
   - Windows line endings;
   - representative quoting and escaping;
   - empty and zero-valued fields where they differ.
7. Add tests for the formatter and an integration test through the public export surface.

## Proof

The independent proof is a byte-for-byte comparison between the new export and the frozen legacy fixture. It must verify column position, footer placement, line endings, quoting, and empty-column preservation.

Also run the existing export tests to prove that the shared writer’s current consumers remain unchanged.

## Complexity avoided

This preserves one data owner and one ordinary report path while adding only the compatibility logic required at the file boundary. It avoids changing the shared writer, duplicating report data, or maintaining synchronization between old and new formats.

## Risks and unknowns

The exact legacy header, field formatting, encoding, and footer syntax are not included in the known facts. Implementation should not proceed past the formatter contract until those details are recovered from the retired script or a known-good file. If no authoritative artifact exists, byte-for-byte compatibility cannot be proved.

Reconsider the dedicated compatibility formatter only if the reconciliation job’s owner explicitly removes the positional file contract or accepts a revised format.
