# Monthly usage report CSV export plan

## Outcome

Add a CSV export that finance can import without changing its spreadsheet workflow. Preserve the old report’s field names and values where finance uses them, but do not reproduce file bytes unless a real consumer requires that compatibility.

The old footer, Windows line endings, and two empty legacy columns have no demonstrated consumer: finance imports by header name, does not compare monthly files, and no API, job, or retained data depends on the bytes.

## Preserved behaviour

- Existing finance-facing column header names and meanings.
- Monthly usage data and totals.
- The application’s existing CSV writer and its escaping rules.
- One export path owned by the application’s report/export code.

The two empty legacy columns and `Total` footer should only be preserved if finance confirms those columns or footer are required by name or import logic.

## Steps

1. Confirm the old header names and identify which of the 14 columns finance actually imports. Treat the retired script or an existing fixture as evidence, not as a compatibility contract by itself.
2. Add the monthly usage report’s field mapping to the existing CSV writer.
3. Compute the total through the report’s existing aggregation logic and include it as report data only if finance requires it. Do not add a special footer formatter merely to match historical bytes.
4. Expose the export through the application’s existing report/export entry point and remove no existing consumer path.
5. Document the supported CSV columns and import expectation at the existing export owner.

## Proof

- Test that the CSV contains the confirmed headers and correct monthly rows.
- Test quoted values, empty values, and numeric totals through the shared writer.
- Test that finance’s spreadsheet import maps each required field by header name.
- Compare parsed columns and values with a known old report; do not compare raw bytes unless a consumer requirement is discovered.

## Complexity avoided

This reuses the existing writer and avoids a second formatter, a permanent legacy column map, Windows-specific line-ending handling, and a fixture that freezes unused footer and empty-column bytes.

## Decision required

If “identical” is an explicit byte-for-byte requirement despite the confirmed consumer facts, the plan changes: add a bounded legacy formatter, preserve all 14 columns, emit the `Total` footer and Windows line endings, and freeze those details with a fixture. That should be an owner-confirmed compatibility decision because it adds maintenance for no currently identified consumer.
