# Plan

Use the existing CSV writer for the monthly usage report and preserve the finance spreadsheet’s header names and data values. Do not reproduce the retired file byte for byte unless finance confirms that the legacy layout is still required.

## Relevant facts

- The retired report used 14 columns, including two empty legacy columns, a `Total` footer row, and Windows line endings.
- Finance imports by column header name and does not compare files between months.
- The application already has a CSV writer that emits headers and data rows.
- No published API, downstream job, or retained data depends on the old bytes.

## Preserved behaviour

- The report remains a CSV export.
- Existing finance-facing column headers remain unchanged.
- Monthly usage values and their meaning remain unchanged.
- The export continues through the application’s existing CSV-writing path.

The empty legacy columns, footer row, and Windows line endings are not currently load-bearing based on the known consumer contract.

## Implementation steps

1. Identify the existing monthly usage report data source and its current column headers.
2. Configure the existing CSV writer with those headers and the monthly usage data rows.
3. Do not add a second formatter, legacy column map, footer handling, or byte-preservation logic.
4. Add a fixture or focused export test asserting:
   - header names and order;
   - representative data values;
   - valid CSV escaping;
   - absence of unintended extra columns or rows.
5. Verify that the generated file imports into the finance spreadsheet using header-based matching.

## Requirement decision

“Identical to the old report” could mean either:

- identical to the old file bytes, which requires the second formatter, legacy columns, footer, Windows line endings, and a frozen fixture; or
- identical in the consumer-visible report fields, which the existing writer can provide.

The known facts support the second interpretation. If byte-level or footer compatibility is later confirmed as a real obligation, preserve the old layout through a bounded legacy formatter and fixture. Until then, adding that machinery would preserve unsupported compatibility and create a second export path.

## Proof and reconsideration

The independent proof is a spreadsheet import using the real header names, supported by automated assertions for headers, values, and CSV structure.

Reconsider this plan only if finance identifies a consumer or workflow that depends on the legacy columns, `Total` footer, exact line endings, or byte-level output.
