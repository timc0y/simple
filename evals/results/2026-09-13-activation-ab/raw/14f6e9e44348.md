The smallest safe plan is to keep the existing sync as the single owner, trigger it from the webhook path, and retain the nightly cron temporarily as a recovery backstop.

### Plan

1. **Document the current contract before changing ownership**
   - Identify what the nightly sync reads, writes to Postgres, and sends to the third-party API.
   - Record its retry behavior, ordering assumptions, transaction boundaries, and completion criteria.
   - Confirm whether the webhook represents a complete sync input or only a notification requiring a follow-up read.
   - Establish the third-party rate limit and expected webhook burst rate.

2. **Trigger the existing sync from each webhook**
   - Reuse the current sync operation; do not create a second implementation.
   - Acknowledge the webhook only after durable handoff to the existing job mechanism.
   - Do not perform the rate-limited API work synchronously in the webhook request unless the current system already guarantees safe latency and retries.

3. **Preserve correctness under duplicates and bursts**
   - Deduplicate by the provider’s event or resource identity.
   - Make the Postgres mutation idempotent, preserving existing rows and avoiding duplicate writes.
   - Enforce concurrency limits and rate-limit-aware retry/backoff for the third-party API.
   - Define behavior for duplicate, delayed, and out-of-order webhooks.
   - Preserve the existing sync’s failure visibility; do not treat a queued job as a successful sync.

4. **Roll out with the cron still enabled**
   - Run webhook-triggered syncs in a canary or limited scope first.
   - Compare webhook-triggered results with the nightly sync’s results.
   - Keep the nightly job available to repair missed events and drain any failed work.
   - Remove or reduce the cron only after the webhook delivery, queue, retry, and reconciliation evidence is satisfactory.

### Must be preserved

- Existing Postgres data and schema semantics.
- The sync’s effective ordering and transaction behavior.
- Idempotency and safe retry after timeouts or partial completion.
- Third-party API rate limits, backoff, and request quotas.
- Recovery for missed, duplicate, delayed, or malformed webhooks.
- Operational visibility: accepted, queued, running, succeeded, failed, retried, and permanently abandoned work.
- Any externally promised webhook response behavior and authentication checks.

### Verification

Verify through the public webhook and sync paths, not only unit tests:

- Replay a real webhook fixture and confirm the expected Postgres state.
- Replay the same event repeatedly and confirm one logical result and no duplicate third-party effect.
- Send a burst at the expected peak rate and confirm queue growth remains bounded, API calls stay within quota, and processing eventually catches up.
- Inject database failures, API throttling, timeouts, and process restarts; confirm retries do not duplicate completed work.
- Compare a controlled webhook run against a nightly-sync run for identical input.
- During rollout, monitor webhook acknowledgement latency, sync lag, retry rate, API quota usage, Postgres conflicts, and reconciliation differences.
- Prove the cron can repair a deliberately missed webhook before retiring it.

Because this workspace has no application or deployment files, the exact owner, queue, identifiers, retry policy, and rollback command remain to be established during step 1. Do not remove the cron or add permanent compatibility machinery until those facts are confirmed.
