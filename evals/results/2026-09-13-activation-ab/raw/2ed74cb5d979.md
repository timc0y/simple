The database can adopt `display_name` while the published REST response continues returning `full_name`.

Before implementation, confirm whether old application instances or external processes read the database column directly. That determines whether a one-step rename is safe.

### Must stay compatible

- The REST endpoint and URL.
- The response field named `full_name`.
- Its existing value, nullability, formatting, and omission rules.
- Existing records: no data loss or unintended value changes.
- Any documented clients, generated schemas, or SDKs that consume `full_name`.
- Database constraints, indexes, defaults, and permissions attached to the column.
- The supported rollback path.

The API serializer should map the new storage field to the old contract:

```text
users.display_name  ->  response.full_name
```

Do not expose `display_name` from the published endpoint unless that is an explicitly separate API change.

### Can change directly

- The physical database column name, if deployment is atomic or all application instances can be upgraded together.
- Internal model/entity/property names from `full_name` to `display_name`.
- Internal queries and repository code.
- New code and internal documentation, provided they do not describe the public API contract.

Keep one stored value. Do not add dual writes or two long-lived columns unless mixed-version deployment or a direct database consumer requires them.

### Migration plan

1. Inventory all references to `full_name`: schema, migrations, models, queries, serializers, request handling, generated API schemas, jobs, reports, and tests.
2. Establish deployment constraints:
   - If old and new application versions can overlap, use a bounded expand/contract migration or an equivalent database compatibility mechanism.
   - If they cannot overlap and no external process reads the column, rename the column and deploy the application mapping together.
3. Create a database migration that renames the column while preserving its type, values, constraints, indexes, defaults, and permissions.
4. Rename internal references to `display_name`.
5. Keep the response serializer explicitly emitting `full_name`.
6. Update API contract tests and internal documentation.
7. Define rollback: restore the application version and reverse the column rename, or provide the corresponding compatibility step for the staged rollout.
8. Remove any temporary compatibility layer only after the supported old application versions and direct consumers have been retired.

### Proof

- Before migration, record row count, null count, and a stable checksum or sample of `full_name` values.
- After migration, verify equivalent `display_name` values and unchanged constraints/indexes.
- Call the published endpoint and assert that it still returns `full_name`, not `display_name`, with unchanged values and status behavior.
- Run tests for reads, writes, nulls, validation, authorization, pagination, and any filtering or sorting involving the name.
- Exercise the actual deployment and rollback procedure in a staging copy with representative data.
- Search the repository and deployment configuration to ensure no unintended `full_name` database references remain; retain only intentional API-contract references.

The key unresolved fact is whether mixed-version application instances or direct database consumers exist. If either does, a direct column rename is unsafe during rollout and the compatibility migration must be staged and given a removal condition.
