Swap them: make the cached CSV the ordinary path, and retain the API as a bounded fallback or cache-refresh path until its contract is disproven.

The six weeks of failures proves the API is not a viable primary path. It does not prove it is safe to delete. Deletion is justified only if all of these are true:

- The CSV satisfies the importer’s full contract, including freshness, completeness, schema, and error handling.
- No consumer, SLA, audit rule, or operational process requires live vendor data.
- The cache has a defined age/validity policy and a recovery path when it is missing or stale.
- Repository and operational searches find no API-specific callers, configuration, credentials, metrics, or persisted state that must remain.
- A successful CSV-only run is verified independently against expected records.
- The API has no near-term obligation or credible repair commitment.

If the CSV is merely a stale emergency snapshot, keep the API and repair it. If the CSV is the accepted source and the API has no remaining obligation, delete the API path and its support code. “Keep it” unchanged is not supported: six weeks of universal failure makes the current primary/fallback arrangement misleading and operationally wasteful.
