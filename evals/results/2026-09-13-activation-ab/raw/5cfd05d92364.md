The smallest safe change is to keep the existing sync as the single owner, trigger it asynchronously from each webhook, and retain the nightly cron temporarily as reconciliation.

### Plan

1. Trace and document the current sync contract: records selected, Postgres writes, third-party calls, retries, pagination, and failure handling.

2. Make webhook receipt enqueue a sync job and acknowledge quickly. Do not perform the rate-limited API call inside the webhook request.

3. Deduplicate jobs by the affected resource and use the provider’s event version or timestamp to avoid applying stale webhooks. Ensure repeated delivery is harmless.

4. Run jobs through one rate-limit-aware worker. Preserve existing backoff, retry, pagination, authentication, and partial-failure behavior.

5. Preserve the existing Postgres transaction/upsert semantics. A failed API call must not produce a falsely successful database state.

6. Run both paths during a bounded canary period:
   - webhooks provide normal updates;
   - nightly cron remains a repair/reconciliation path;
   - compare webhook-driven results with nightly results and inspect missed, duplicated, stale, and failed events.

7. Remove or disable the cron only after webhook delivery, enqueueing, processing, and reconciliation metrics remain healthy for an agreed period. Keep a manual reconciliation procedure.

### Must be preserved

- The sync’s externally visible data and write semantics.
- Idempotency under webhook retries, worker retries, and timeouts after a third-party call may have started.
- API rate limits, retry-after handling, bounded concurrency, and backoff.
- Webhook authentication and fast acknowledgement behavior.
- Recovery for dropped events, out-of-order events, worker failure, and third-party/API downtime.
- The nightly job until the new path has demonstrated it can replace its reconciliation role.

### Verification

Before rollout, use the existing sync tests or fixtures to prove that a webhook-triggered job produces the same Postgres result as the nightly sync.

During canary, measure and alert on:

- received versus accepted webhooks;
- queued, started, completed, retried, permanently failed, and deduplicated jobs;
- processing latency and queue age;
- third-party requests, throttles, retry-after responses, and error rates;
- Postgres write failures and records whose source version regresses;
- differences found by nightly reconciliation.

Test duplicate, out-of-order, malformed, authenticated, API-throttled, API-timeout, database-failure, and worker-restart cases. The migration is complete only when webhook delivery is accounted for, rate limits remain within bounds, and reconciliation finds no unexplained divergence.

The repository contains no implementation or operational documentation beyond the request, so exact owners, queue capabilities, event identity, and existing retry/idempotency guarantees must be established before choosing the wiring.
