The smallest safe change is to keep the existing sync as the single owner and change only its trigger:

`webhook → durable, deduplicated sync job → existing sync → Postgres and third-party API`

Do not run the full sync inline in the webhook request. Webhook retries, bursts, and provider latency would make request handling and rate limiting unsafe.

## Plan

1. **Inventory the current owner before changing it.**

   Identify the cron entry point, sync function, Postgres transaction boundaries, API retry/rate-limit handling, idempotency keys, and existing job/queue mechanism. Confirm whether webhooks can be duplicated, delayed, or delivered out of order.

   If no durable asynchronous job mechanism exists, stop and design the smallest one backed by an existing platform or Postgres. Do not use in-memory buffering.

2. **Make each webhook request a sync trigger.**

   Reuse the existing sync owner. Have the webhook enqueue or signal a durable job containing the affected entity or synchronization scope.

   Deduplicate equivalent pending work, or make execution idempotent so duplicate webhooks cannot duplicate database rows or third-party mutations. A webhook should acknowledge only after the trigger is durably recorded.

3. **Preserve the sync’s safety contracts.**

   Preserve:

   - Existing Postgres transaction and uniqueness constraints.
   - Existing API rate limiting, retry rules, and handling of permanent versus transient errors.
   - Idempotency and reconciliation after timeouts, since a timed-out API call may already have succeeded.
   - Ordering requirements, if later webhook state must not be overwritten by an older event.
   - Existing logging, metrics, alerting, and manual retry behavior.

   Add bounded concurrency and backpressure so webhook volume cannot exceed the third-party API budget.

4. **Run both triggers temporarily.**

   Keep the nightly cron as a reconciliation path during a defined soak period. It must remain idempotent and must not create duplicate API work. Compare nightly reconciliation results with webhook-triggered processing.

   Disable cron only after the webhook path has demonstrated complete processing and the reconciliation run shows no unexplained drift. Retain a manual reconciliation operation if operators currently depend on it.

5. **Define rollback before rollout.**

   Use a reversible trigger switch or deployment rollback:

   - Stop accepting new webhook-triggered jobs.
   - Drain or safely retry already-recorded jobs.
   - Re-enable cron.
   - Do not delete queued work or partially applied state.

## Verification

Before rollout, establish a baseline from the current cron path:

- sync success and failure counts;
- Postgres row/state changes;
- third-party API request volume, throttling, and error rates;
- sync latency and backlog;
- duplicate and retry behavior.

Verify the new path with:

- duplicate, reordered, delayed, and burst webhook deliveries;
- worker restart and database/API timeout scenarios;
- third-party `429` responses and transient failures;
- a sync that succeeds in Postgres but fails at the API, and the reverse;
- confirmation that one logical webhook event produces one intended final state;
- end-to-end checks that a received webhook reaches Postgres and the third-party API;
- reconciliation showing no drift while cron and webhooks overlap.

The migration is not ready to remove cron until durable acceptance, idempotency, rate-limit protection, recovery after uncertain API outcomes, and observable backlog/error handling are all demonstrated. The repository contains no implementation evidence, so the first inventory step is required before choosing the exact queue, keys, or rollout controls.
