The safe target is:

- Database storage: `users.display_name`
- REST response: still returns `"full_name"` with the same value and JSON shape
- Internal application code: uses `display_name`

The published API contract must remain compatible. Existing clients may depend on:

- The `full_name` response key
- Its value, nullability, and string semantics
- Response status codes and surrounding payload shape

Do not rename the REST field unless there is a separately versioned API and an agreed deprecation period.

## Plan

1. Inventory the actual consumers

Search for:

- `users.full_name` in migrations, SQL, models, queries, views, reports, jobs, and tests
- The endpoint’s serializer or response schema
- Direct database consumers and supported application versions
- Constraints, indexes, triggers, generated columns, and views involving `full_name`
- Deployment behavior: atomic release or rolling/mixed-version release

The deployment model determines whether the database rename can happen in one step.

2. Change the application’s internal owner

Update the user model, queries, validation, and internal references to use `display_name`.

Keep the endpoint serializer explicit:

```json
{
  "full_name": "Ada Lovelace"
}
```

It should map `display_name` to the existing public key `full_name`. Do not rely on automatic model serialization, because that could accidentally publish `display_name`.

3. Choose the schema migration path

If the application and schema change are deployed atomically, or old application instances cannot run during the migration:

- Rename `users.full_name` to `users.display_name` using the database’s supported rename operation.
- Preserve existing values, constraints, indexes, and permissions.
- Deploy the application mapping at the same release boundary.

If rolling deployment leaves old instances running:

- Add `display_name`.
- Backfill it from `full_name`.
- Temporarily write both columns and have the new application read `display_name`.
- Keep the API serializer returning `full_name`.
- After all old instances and direct consumers are retired, validate equality, stop dual writes, and remove the old column in a later migration.

Do not use two columns or dual writes unless mixed-version operation requires them. The published API alone does not require duplicate database storage.

4. Update the durable contract

Update the schema/model documentation and API contract tests so they state the distinction:

- `display_name` is the internal/database name.
- `full_name` is the stable REST response name.

## What can change directly

These can change with the new schema:

- Internal model property names
- SQL references owned by the application
- Repository/service method names
- Internal documentation and generated database mappings
- New migrations and schema metadata

These must not change directly:

- The REST response field `full_name`
- Existing stored values
- Any externally supported direct database interface
- Behavior clients observe for nulls, empty strings, encoding, and response shape

## Proof

Verify at each boundary:

- Migration test on a copy of the schema: `full_name` becomes `display_name`; row count, values, nullability, indexes, constraints, and permissions are preserved.
- Data validation: compare old and new values for every migrated row, using counts and a deterministic aggregate/checksum where practical.
- API contract test: call the published endpoint and assert that it still returns `full_name`, never `display_name`, with unchanged values and payload shape.
- Application tests: exercise reads, writes, validation, ordering, filtering, and any user-related jobs against `display_name`.
- Mixed-version test, if rolling deployment is used: old application + new schema and new application + transitional schema must both work.
- Deployment rehearsal: run the migration and rollback procedure against production-like data and measure lock duration.

Rollback must be defined before release. A pure database rename is usually reversible; the expand/contract path requires restoring the old column from the new value or retaining the old column until the new release is proven.

The key unresolved fact is whether old application instances or external systems read the database column directly during deployment. If not, use the single-column rename plus API mapping. If yes, use the bounded transitional migration and remove it once those consumers are gone.
