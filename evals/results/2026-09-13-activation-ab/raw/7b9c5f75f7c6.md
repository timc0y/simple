The repository gives no evidence beyond the prompt: no implementation, callers, tests, provider clients, or channel-specific policy. A third case is not automatically an architectural failure. First check whether the existing function still owns one coherent operation—choosing a channel, validating its input, invoking the provider, and translating errors.

Before implementing, I would inspect:

- All callers and whether they depend on the function’s return value, errors, ordering, or retries.
- The switch’s actual complexity: provider credentials, payload construction, rate limits, retry/idempotency, and failure semantics per channel.
- Existing email/SMS tests and provider fakes.
- Configuration and dependency boundaries for a push provider.
- Whether notification preferences, templates, audit records, or delivery status differ by channel.
- Operational requirements: metrics, logging, timeouts, retries, and partial failure behavior.

Decision rule: if push only adds one provider-specific branch, add the case and test it. If each channel has independently changing policy or the switch forces callers to understand channel details, extract a small internal handler/strategy boundary while adding push. Use an interface only when there is a real consumer and a stable contract—not merely because another channel is planned.
