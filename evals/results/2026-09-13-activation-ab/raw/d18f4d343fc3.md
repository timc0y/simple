## Outcome

Run the existing sync when a webhook arrives, but keep the nightly cron temporarily as a recovery path. The webhook should enqueue work; it must not call the third-party API inline or delay the webhook response.

## Relevant fact

The repository contains only the request, not the sync implementation, schema, webhook handler, or tests. The plan therefore preserves the existing sync owner and requires those details to be confirmed before implementation.

## What must be preserved

- The sync’s current Postgres writes, transaction boundaries, validation, and error handling.
- Its third-party API authentication, pagination, rate-limit handling, retries, and backoff.
- Idempotency: webhook retries and duplicate deliveries must not duplicate writes or API work.
- Ordering or version checks, if newer webhook data must not be overwritten by older work.
- The nightly cron until webhook delivery and recovery are proven reliable.
- Observability: sync success, failure, retry, throttling, lag, and permanently failed work.

## Smallest safe plan

1. Identify the existing sync function or job as the sole owner of synchronization. Make the webhook trigger that owner instead of introducing a second implementation.

2. On each webhook, validate authenticity and extract the stable upstream object/event ID. Record or enqueue a durable sync request keyed by that ID, then acknowledge the webhook promptly.

3. Reuse the existing worker or job mechanism if one exists. If none exists, add only the smallest durable work queue supported by the current deployment and Postgres setup.

4. Enforce deduplication at the durable boundary with a unique event/object key. Repeated webhooks should merge into or reuse pending work rather than create unbounded duplicate jobs.

5. Apply the third-party API rate limit in the worker shared by all sync triggers. Use bounded retries and backoff for retryable failures; retain failed work for inspection or replay. Do not retry permanent validation or authorization failures indefinitely.

6. Run webhook-triggered syncs in production while the nightly cron remains enabled as a backstop. Ensure cron uses the same sync owner and deduplication rules.

7. Remove or reduce the cron only after the recovery and reliability evidence below is met. If webhooks cannot guarantee delivery or replay, retain a lower-frequency reconciliation job rather than deleting the only repair path.

## Verification

Before rollout:

- Unit or integration tests prove duplicate webhook delivery causes one effective sync.
- Tests prove a timeout or worker restart after the API call does not create duplicate Postgres records or unsafe repeated mutations.
- Tests prove rate limits are respected under a burst of webhooks.
- Tests prove retryable API failures retry with backoff and permanent failures become visible failures.
- An end-to-end test verifies: webhook accepted → durable work recorded → sync runs → expected Postgres state is committed.
- A reconciliation check compares webhook-triggered results with the current nightly-sync result for representative objects.

During rollout, verify:

- No increase in duplicate rows, conflicting updates, API throttling, failed jobs, or webhook response latency.
- Sync lag stays within the required freshness target.
- Every accepted webhook has either a successful sync, a pending retry, or an operator-visible failure.
- The nightly backstop finds no material missed changes over an agreed observation period.

The cron is safe to retire only when webhook delivery is durable or replayable, failures are observable and recoverable, and reconciliation shows no missed updates. Otherwise, replace it with a less frequent reconciliation job rather than removing it.
