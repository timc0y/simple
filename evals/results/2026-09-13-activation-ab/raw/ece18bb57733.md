## Required compatibility

Keep the published REST response unchanged:

- JSON field remains `full_name`.
- Its value, type, nullability, omission rules, and formatting remain unchanged.
- Existing clients must not need to change.
- Existing database values must be preserved exactly.

The internal name does not need to match the API name. Store `display_name`, then map it to `full_name` in the existing response serializer.

## What can change directly

If the application is the only database consumer and schema/application deployment can be coordinated:

- Rename `users.full_name` to `users.display_name` with a database migration.
- Update ORM models, queries, validation, writes, indexes, and internal references.
- Keep the API serializer explicitly returning `full_name`.
- Update internal tests and documentation that describe the storage model.

Do not add two stored columns or dual writes unless another process still reads `users.full_name`.

The repository provided contains only the request, so direct database consumers, deployment strategy, and rollback guarantees remain to be confirmed.

## If rolling deployment or external SQL consumers exist

Use an expand-and-contract migration:

1. Add `display_name`.
2. Backfill it from `full_name`.
3. Deploy code that reads and writes `display_name` while the API still emits `full_name`.
4. Keep the old column synchronized only for the period required by old application instances or external consumers.
5. Verify all consumers have migrated.
6. Remove `full_name` in a later migration.

The compatibility period needs a named owner and removal condition.

## How to prove it

- Search application code, migrations, jobs, reports, and integration repositories for `full_name`.
- Test migration preservation: row count, null counts, and representative values before and after.
- Run the API contract test and assert the response still contains `full_name`, not `display_name`.
- Test create and update flows to prove the API value is backed by `display_name`.
- Test old records, null/empty values, authorization, and error behavior.
- Validate indexes, constraints, and query plans after the rename.
- Exercise the documented rollback procedure, including whether data written after deployment remains recoverable.

The success invariant is: storage uses `display_name`, while existing REST consumers observe no contract change.
