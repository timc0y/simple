The published REST contract must keep returning `full_name`. Rename the database field internally, then map `display_name` to the existing API field.

## What must stay compatible

- Existing REST response shape: `full_name` remains present with the same value, nullability, and format.
- Existing clients, URLs, status codes, and error behaviour.
- All stored user values.
- Any supported older application instances or direct database consumers, if they exist.
- Constraints, indexes, triggers, ORM mappings, exports, and background jobs that depend on the column.

The API should make the translation explicit:

```text
database: display_name
response: { "full_name": user.display_name }
```

Do not expose `display_name` unless introducing it as a separately versioned API change.

## What can change directly

If deployments are atomic and the application is the only database consumer:

1. Add a migration that renames `users.full_name` to `users.display_name`.
2. Update models, queries, serializers, validations, fixtures, and internal references.
3. Keep the REST serializer returning `full_name`.
4. Deploy the migration and application change as one coordinated release.
5. Remove obsolete internal references to `full_name`.

Do not retain two database columns or dual-write unless rollout evidence requires older code to run against the database at the same time.

If rolling deployment or direct database consumers are supported, a direct rename is unsafe. Use an expand/contract migration instead: introduce `display_name`, backfill it, make the application transition safely, preserve the old access path during the compatibility window, then remove it only after all old consumers are gone.

## How to prove it

Before migration:

- Inventory code, migrations, jobs, exports, reports, and database clients that reference `full_name`.
- Confirm the deployment model: whether old and new application versions can overlap.
- Record row counts, null counts, and representative values.

Tests and checks should prove:

- The migration preserves row count and every `full_name` value.
- The new schema has `display_name` with the same constraints and indexes.
- The REST endpoint still returns `full_name`, not `display_name`.
- Responses before and after the change are equivalent for representative users, including null, empty, Unicode, and long names.
- Application reads and writes use `display_name`.
- No supported consumer still requires the old database column after the compatibility window.

Operational proof should include a staging migration against a production-shaped copy, deployment smoke tests, and a tested rollback procedure. Rollback must account for both application version and schema state; a database rename is not safely reversible once newer code has been deployed unless the reverse migration is verified.

The unresolved decision is whether mixed-version deployment or direct database access is supported. That fact determines whether the simple atomic rename is sufficient or an expand/contract rollout is required.
