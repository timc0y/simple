I’d split the channel-specific behavior now, but not introduce a class hierarchy by default.

Push is an explicit near-term requirement, not a hypothetical future. A third branch will likely make the current function own provider APIs, payload formatting, credentials, retries, and error semantics for three unrelated channels. Extract a small channel boundary—an interface or function contract—with email, SMS, and push implementations behind it. Keep the existing public notification function as the policy/orchestration owner.

Prefer plain modules/functions over classes unless the repository already uses classes or handlers need lifecycle/state. The boundary should earn its cost by isolating channel-specific knowledge; it should not become a pass-through abstraction.

Before implementing, I’d check:

- The module’s public API and every caller: what must remain compatible?
- Existing tests, especially assertions about provider calls, retries, ordering, and errors.
- Whether email/SMS already differ in templates, recipient validation, scheduling, opt-in, or fallback policy.
- Provider clients, SDK versions, configuration, secrets, and how push tokens are stored and invalidated.
- Whether notifications are synchronous, queued, retried, or idempotent; a timeout may already mean delivery started.
- Logging, metrics, tracing, and operational alerting expectations per channel.
- The actual push contract: platforms, payload shape, token lifecycle, consent, delivery status, and failure handling.
- Existing repository conventions for interfaces, dependency injection, modules, and test doubles.

If those checks show that the switch is tiny, stable, and the three channels share the same semantics, adding one case could be the smallest safe change. But given “growing” behavior plus a committed third channel, I’d establish the boundary now while preserving the current caller contract and avoiding unrelated redesign.
