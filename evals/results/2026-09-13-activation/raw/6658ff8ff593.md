Recommendation: add push as another case for now. Do not introduce per-channel classes and an interface solely because push is planned next month.

The repository available here contains only the prompt, so there is no evidence that the switch is currently causing real complexity. A class hierarchy would add concepts, files, lifecycle rules, and tests before we know they remove work. Keep the existing notification owner and public function stable; add push through the same path.

Before implementing, I would check:

- Every caller and the public input contract: channel values, payload shape, return value, and error behavior.
- Whether email and SMS already have materially different policies—retries, scheduling, templates, provider credentials, rate limits, or delivery status.
- Whether push introduces a genuinely different recipient model, such as device tokens, multiple devices, platform-specific payloads, or token invalidation.
- Provider integrations and dependency ownership, including configuration and observability.
- Existing tests, fixtures, and mocks that define the switch’s behavior.
- Whether the function is synchronous, queued, idempotent, or allowed to partially succeed.
- Whether push is a one-off addition or a committed pattern for several more channels.

If those checks show each channel owns substantially different state and failure behavior, extract a small channel strategy boundary then—probably with concrete handlers and a dispatcher, not an elaborate interface hierarchy. If push only needs another provider call and shared validation/retry behavior, another case is the simpler truthful design.
