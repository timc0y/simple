The smallest safe plan is to keep the existing sync logic as the single owner, trigger it through durable asynchronous work created by each webhook, and retain the nightly cron until the new path proves equivalent.

## Plan

1. **Record the webhook event durably.**  
   In the same Postgres transaction as the webhook’s accepted state, create or upsert one pending sync item keyed by the source event or entity ID. A duplicate webhook must not create duplicate work.

2. **Run the existing sync asynchronously.**  
   Reuse the existing worker or job mechanism if one exists. Do not call the third-party API inside the webhook request. If no worker exists, use a small Postgres-backed work queue with claiming, retry state, and a dead-letter/manual-retry state.

3. **Preserve the sync’s current safeguards.**

   - Existing Postgres transaction and consistency rules.
   - Idempotency, so retries and duplicate webhooks converge to one result.
   - Existing API authentication, request shape, pagination, and error handling.
   - A shared rate limiter and bounded concurrency across all workers.
   - Retry only transient failures, with backoff; retain permanent failures for inspection.
   - Enough event/entity identity to reconcile a failed or delayed sync.
   - The nightly cron as a temporary reconciliation safety net.

4. **Deploy in two stages.**

   - First, add durable webhook-triggered work while the cron remains enabled. Suppress duplicate execution through the same idempotency key or claim mechanism.
   - Compare webhook-driven results with the cron’s reconciliation results over a representative period. Then disable the cron only after no unprocessed or unexplained backlog remains and operational owners accept the metrics.

5. **Retain reconciliation.**  
   “Every webhook” must not be the only recovery path. Keep a manually runnable or less-frequent reconciliation operation for missed webhooks, historical drift, and third-party outages. It must use the same sync owner and rate limiter.

## How it is verified

Verify through the public webhook-to-sync path, not only unit tests:

- Deliver the same webhook repeatedly and confirm one effective sync and no duplicate Postgres effects.
- Deliver a burst larger than the third-party API limit and confirm webhook responses remain healthy, work is durable, API calls stay within the configured limit, and backlog drains.
- Inject worker crashes, timeouts, API throttling, and permanent API errors. Confirm retries do not duplicate writes, throttled calls back off, and permanent failures remain visible and retryable.
- Compare the old nightly result and webhook-driven result for the same fixtures: Postgres state, third-party calls, error classification, and counts.
- Restart the worker and database connection during pending work; confirm claimed work is recoverable.
- Before removing cron, verify zero unexplained pending items, no growing retry/dead-letter set, bounded processing latency, and successful reconciliation over the observation window.

The repository contains no implementation beyond the request, so the existence of a worker, queue, idempotency key, and current sync contract must be established before choosing whether to reuse them or add the minimal missing mechanism.
