# Recover context and improve the method

Use this when the user asks to recover history, learn from sessions, update a skill or capture a repeated working convention.
`repository-work.md` owns ordinary continuation after a correction or interruption.

## Recover evidence

Start with the active request, current tree and existing knowledge owners.
Narrow history by repository, topic and time before reading large session records.
Use the host's available history tools or local exports; do not assume a particular session database exists.
Preserve the user's scope when they explicitly request a broader crawl.

Track the inspected sources and coverage limits.
Separate user requests, agent proposals, accepted decisions, completed actions and observed results.
Check historical conclusions against current code and state before reuse.
Keep rejected approaches with the reason they failed when that prevents repeated investigation.

For large payloads, use targeted queries or bounded readers with exact source pointers.
Keep decision-changing excerpts in the main context and bulk evidence in its local owner.
Truncation means unread material remains; an inventory alone is not a semantic review.

## Turn a correction into a durable improvement

Identify whether the problem came from missing guidance, failed retrieval, ambiguity, conflicting rules, missing tools or a weak check.
Repair that cause in the smallest existing owner.
Use a structural constraint or tool when it can prevent the repeated mistake.
Keep personal conventions in local guidance and repository facts in the repository's owner.
Public shared guidance must stand on its own without private transcripts or client examples.

Use a decision trail for a long investigation or experiment when later work needs its rejected branches.
Each record needs the question, evidence, decision, artifact and remaining uncertainty.
Reuse an existing result file or knowledge owner. A short task needs no new log.
Keep private raw evidence ignored and separate from self-contained public examples.

## Author or update a skill

Confirm the user outcome and the existing skill that should own it.
Use available skill-authoring guidance for the host's actual format and validator.
Keep the skill usable without another plugin unless the workflow truly needs that dependency.
Put conditional procedures behind clear task routes instead of registering another skill for every lesson.

Before changing guidance, map each affected meaning to its surviving instruction, example or check.
Preserve the reason, countercase and uncertainty as well as the headline rule.
Validate the package, paths and runnable helpers.
Exercise a realistic task with the final skill when the change can materially affect agent behaviour.
Check retrieval and task outcome separately.
Preserve negative results; a weak evaluation is not permission to discard wanted capabilities.

Report the local change and its evidence separately from installation or publication.
Use the existing authority for each external transition.
